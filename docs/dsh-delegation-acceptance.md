## 1. 验收对象与方式

验收对象是第一阶段交付的完整工具链：

- dsh/tw-tool-subagent.js：定向选模委派工具（档位 / 精确 provider、model、effort 两种调用）；
- dsh/inject.js：子代理创建期模型注入（直接选择通道 + header 回读通道 + 迁移期旧标签链）；
- dsh/index.js：插件装配与 systemPrompt 决策表 section；
- dsh/client/badge.js：模型席位徽标、@junior/@senior/@expert 输入候选、全局档位配置卡。

实机方式：插件经真实 DSH Web 宿主装载后，人工在界面创建、续聊、重启子代理并逐项核验。核验载体有三：

1. **子代理右下角模型/effort 徽标**——人工可见核验。方案 §9 第 5 条裁决确立：模型与 effort 实际生效由徽标展示承载，工具不做运行期对账（见 §3 缺陷 3）。
2. **宿主日志**——注入路径的 info 日志（「直接选择注入」「header 回读重建」「标签注入」「补读注入」）标明每次注入走了哪条通道。
3. **会话请求记录**——子会话持久化的 request/header.config 是 provider/model/effort 的持久化事实源。

自动套件随验收实测回归（结果见 §5）。

## 2. 七项验收逐条记录

### 第 1 项：档位、精确模型、effort 创建 —— 通过

**要求**（方案 §7 第 1 条）：分别用档位、精确模型和 effort 创建子代理，子代理右下角模型/effort 徽标展示与指定值一致。

**实测**：三种方式各创建子代理，创建字段齐全，徽标展示的 provider/model/effort 与指定值一致。档位方式按全局 tiers 配置的候选数组稳定取第一项；精确方式按显式传入值原样生效；effort 随创建注入并在徽标可见。

**机制依据**：档位与显式选择都先经 resolveCallConfig() 在创建前验证，失败不建会话；selection 与 agentOptions 由同一份验证结果派生（方案 §10.3 风险 2 的单一来源约束），不存在两处各解析一遍导致的不一致。

**自动证据**：用例「execute 成功（档位带 effort）：spec 与返回卡」「显式精确选择不得被 resolveCallConfig 静默改写」「档位未配置 → TW_SUB_TIER_UNRESOLVED，未创建子会话」。

### 第 2 项：并行创建两个不同模型的子代理不串线 —— 通过

**要求**：并行创建两个不同模型的子代理，会话与模型徽标均不串线。

**实测**：同进程并行创建两个不同档位/模型的子代理，两会话各自请求使用各自指定值，徽标互不串线。

**机制依据**：内存待注入选择按 sessionId 隔离（Map 结构，键为插件预生成的 childId），注入贡献函数按自身 agent.id 取用且命中即删（take-once），两次独立创建天然互不可见对方的选择。

**自动证据**：用例「并行创建两个不同模型，选择按 sessionId 隔离不串线；selection 与 agentOptions 同值」。

### 第 3 项：续聊保持原模型和 effort —— 通过

**要求**：子代理完成一轮后，send_message 续聊仍使用原模型和 effort。

**实测**：对已创建的子代理续聊多轮，每轮请求的模型与 effort 保持创建时的指定值，徽标不变。

**机制依据**：模型选择安装器注册的监听器在 setup 返回后持续在场，显式释放才注销；续聊不重建子会话，每次请求都继续被同一 selection 覆写。

**自动证据**：用例「直接选择与冷恢复在 setup 返回后保持监听器，显式释放时才注销」。

### 第 4 项：重启 DSH 后恢复子会话，provider/model/effort 不变 —— 通过

**要求**：重启 DSH 后恢复子会话，provider/model/effort 不变。实现依赖：provider/model 由持久化 agentOptions 承载；effort 由 setup 阶段从持久化 request/header.config.reasoningEffort 回读重建（方案 §10.3 风险 1）。

**实测**：重启宿主后子会话以恢复（reason=resume）方式重建，恢复请求 header 中的 provider/model/effort 与重启前精确保持一致，徽标不变。

**机制依据**：插件内存的直接选择在重启后为空，注入贡献函数随即从同一会话持久化的最近 request/header 回读重建 selection（recallFromHeader）：provider/model 是权威来源，effort 有值才附带；无 effort 的会话同样锁定 provider/model，防止迁移期旧标签链把已确认的选择改写回默认模型。

**自动证据**：用例「cold-resume 的 header 优先于合法标签链，保持持久化的已确认选择」「cold-resume 的无 effort header 优先于合法旧标签链」「无直接选择时按 header 回读重建（effort 冷恢复路径）」。

### 第 5 项：完整 team-work 任务全链路 —— 通过（二阶段切链后，2026-09-06）

**要求**：执行一个完整 team-work 任务，首派、agent-map、续派、评审和门禁全链路正常。

**要求**：用升级前的旧子代理做跨版本恢复，确认清理前只读兼容有效。

**实测**：升级前创建的旧子代理（不经新工具创建、携带旧标签链）跨版本恢复有效，模型选择不回退默认，旧链只读兼容行为符合预期。

## 3. 实机过程发现并修复的缺陷

实机验收当日先后暴露三个缺陷，均已修复并带回归锁定。时间线：交付（10:41）→ 缺陷 1（11:37 修复）→ 缺陷 2（11:56 修复）→ 缺陷 3 两轮（12:14 限时轮询、12:27 用户裁决砍除）。

### 缺陷 1：客户端 inject 声明缺失 —— @ 档位候选不显示

- **症状**：插件装载后，Web 输入框 @ 列表中没有档位候选，@expert 无联想。无报错，静默失效。
- **根因**：DSH 客户端上下文只注入已声明的服务（与既有客户端扩展的做法一致）。客户端 bundle 未在 inject 数组声明 inputTriggers，运行时按可选查询拿不到该服务，@ 候选源静默降级、未注册。
- **修复**（提交 399e825）：inject 数组补入声明；运行时判空降级保留作双保险（客户端缺该服务时仅关闭 @ 候选，工具调用与自然语言委派不受影响）；契约测试同步。
- **同类根因一并修复**（提交 83af07f 与 399e825，方案 §10.5 有记录）：宿主侧实现曾以直接属性访问探测未声明服务，触发依赖注入框架的「without inject」守卫异常并阻断 Web 装载。统一改为可选查询（ctx.get()），覆盖宿主的 systemPrompt 与工具执行期的 llm、sessions、sessionPersistence 查询；并加严格 Context 守卫回归，锁定「未声明服务禁止直接属性访问」。

### 缺陷 2：@ 候选 candidates 未返回 Promise —— @ 菜单崩溃

- **症状**：缺陷 1 修复后实测 @，整个 @ 菜单崩溃，报 TypeError: source.candidates(...).then is not a function。
- **根因**：宿主输入触发控制器对候选函数的返回值直接调 .then，契约要求 Promise；实现返回了同步数组。
- **修复**（提交 159145b）：候选函数用 Promise.resolve 包装返回值；单测补 thenable 契约断言防回归。

**伴随改进**（提交 36c63d3）：@ 档位候选的选中写入从提示词文本改为插入式标记（与文件/会话引用一致的 chip 形态），提交时经编解码器序列化为模型可读的委派指令，剪贴板与持久化投影保留 @档位 原文。

### 缺陷 3：首请求 header 运行期对账越界砍除（用户裁决）

- **背景**：第一阶段初版自带「首请求 header 严格核验」——启动后核对子会话首个请求 header 的模型字段与指定值是否一致，不一致即回收子会话。这是评审链引入的额外核验，不是产品需求。
- **实机第一轮**：startContinuable 返回时首个 LLM 请求尚未发出（收件箱接受不等于请求已执行），事件流中还没有 request/header，立即核验把健康子会话误判为错配（TW_SUB_FIRST_REQUEST_MISMATCH）并回收。子代理日志实证其描述符模型正确、启动后数十毫秒即被父级中止——立即对账必然误杀健康会话。
- **中间修复**（提交 8eb19a4）：改为限时轮询（默认 10 秒、150 毫秒间隔）：header 出现即核验，超时未出现报「待落盘」与真错配区分；补延迟落盘命中与超时两条回归。当时全量套件 214 用例通过。
- **用户裁决砍除**（提交 df828f0，2026-09-01，方案 §9 增量 5）：整体砍除首请求 header 运行期对账。理由：该核验是评审链引入的额外需求而非产品需求——模型/effort 实际生效的核验由子代理右下角徽标展示承载即可（人工可见）；实机两轮证实立即对账必然误杀，限时轮询属于为额外需求引入的额外复杂度，一并移除。启动确认语义回归为「持久化服务在场 + flush 参与」。
- **同步落点**：方案 §4/§7/§9 与 roadmap 同步修订；自动用例锁定「不做首请求 header 运行期对账，flush 确认即成功」。失败清理路径的回收能力保留（创建失败、持久化确认失败时仍统一回收且回收失败禁止重试）。

## 6. 评审留档时序关注项的核验结论

方案 §7 留档了三项实机关注项，本轮核验结论：

1. ~~flush 后首个 header 可见时序~~——已随首请求 header 对账砍除而失效（见 §3 缺陷 3），不再需要核验。
2. **宿主 startContinuable 是否尊重传入 childId**——实机证实尊重：直接选择通道按预生成 sessionId 命中注入（若宿主忽略传入 id 自行生成，直接选择必然 miss 且 effort 静默丢失，而实机注入命中、徽标一致）。该风险可关闭。
3. **drainContinuableChildren 的停止完成语义**——曾在对账回收路径实际使用，行为符合预期（停止并回收目标子会话）；对账砍除后该能力保留在失败清理路径，语义结论不变。
