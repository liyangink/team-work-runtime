# team-work-runtime 的工作模型：波次、轮次，与你能分配的最小工作单元

> 本文讲概念，不凹代码。对象是一个以「任务目录即状态」承载多智能体协作的研发运行时：任务怎么被拆成工作，工作怎么被推进，状态从哪来，以及——为什么「灵活度」被画了一条明确的线。

## 从一次返工说起

一个方案评审任务走到了人工门，用户选择返工。接下来发生了三件看起来互不相干的事（另有第四件故障：成员用决定前的旧派单重交、被误认成返工完成，跳过应有的返工——其教训见下文「决定」条目）：

1. 同一张返工单被发给了 Owner 三次，内容完全相同，只是编号不同；
2. 续派两轮之后，系统报「找不到原成员」，而那个成员其实还在；
3. 评审明明已经通过，波次机却一遍又一遍地派评审，任务再也走不到下一道门。

修掉任何一件事都只需要一个局部补丁。但我们最终发现，三件事共享同一个根因：**波、成员、轮次——这几个概念在系统里没有自己的实体身份，全靠「偶然一致的字段」互相代偿。字段一旦不一致，代偿就塌了。**

这就是本文的起点。我们先把这些概念一个个讲清楚：它们是什么、彼此什么关系、状态从哪里来、能力边界画在哪。

## 一个类比建立直觉

把一次团队协作任务想象成一张订单：

| 概念 | 类比 |
| --- | --- |
| 任务 | 一整份订单 |
| 阶段 | 订单上的一道工序（设计、加工、质检……） |
| 包 | 工序里可并行的工位 |
| 波 | 工位上的一次动作（开工 / 返工 / 检验 / 专家把关） |
| 派发 | 发给某个工人的一张工单 |
| 报告 | 工人交回的工单结果 |
| 轮次 | 这个工位返工了几圈 |
| 成员 | 工人本人——工单换，人不换 |
| 制品 | 工件，每次交付一个新版本 |
| 门禁 | 工序的质检关 |
| 决定 | 客户或质检的拍板记录 |

下文用这个类比做锚点，把每个词钉成精确的定义。

## 术语表

### 任务

一次完整的协作工作，有自己的名字和目录，项目内名字唯一。生命周期：创建 → 推进 → 完成 → 归档。归档后只读。

### 阶段

任务按研发流程切的大段：调研、方案设计、实施、测试、代码审查、收尾……任务在任意时刻**站在且只站在一个阶段**。阶段是工作流定义里静态声明的，名字稳定——这是后面一切「可寻址性」的地基。

### 包

把一个阶段的工作拆成的块。每个包有自己的可写文件、完成标准和依赖关系。拆分是可选的：不拆就是单包。包的意义是让互斥的工作可以**并行交给不同成员**。

### 波

波次机「推进一步」给出的动作：**该谁干活、干什么**。一共四种（另有 gate 与 converge-user 两种**停止派波状态**）：

- **produce**：让 Owner 首次交付
- **respond**：让 Owner 返工修订
- **review**：让 Challenger 评审
- **verdict**：让 Expert 裁决（仅核心场景）

波是推进的原子步：波次机一次只推出一个波，这个波被报告消费后才推下一个。**波与波之间永远是串行的。**

### 派发

一个波落实到**具体某个成员**的工作单：派单全文、编号、可写范围。一个波通常产生一张派发；多包时一个波产生多张——每个已解锁/被包含的包一张，**这些派发并行执行**（依赖未解锁、尚未派发的包不在之列）。所以准确的并行语义是：串行的是波，并行的是派发。

### 报告

成员交回的结果。Owner 的交付报告（做了什么 + 登记了哪些文件），Challenger / Expert 的评审报告（结论 + 问题清单 / 裁决）。报告是事实：**身份 = 派单 key + 版本号（ver）**，最新版正文落在单文件，修订即版本 +1（同 key 同内容重交幂等返回）；历史版本经审计日志的 ver + payloadDigest 链即时可审计，全文留档为后置项。

### 轮次

**同一个包被打磨的代次**：Owner 第 1 次交付是第 1 轮，被打回修订再交是第 2 轮。轮次绑定包，而不是任务。一轮的完整形态 = 一次 Owner 交付 + 一次 Challenger 评审（核心场景再加一次 Expert 裁决）。自主收敛上限是三轮，到达上限仍未收敛就交用户决定。

### 成员

一个**持续存在**的干活者：某个 Owner、某个 Challenger、某个 Expert。一次任务里，同一个角色槽位通常从头用到尾——续派的意思是「让同一个人继续干」，而不是换人。平台层对应一个可续聊的子会话。成员的生命周期跨越多张工单，这正是它不能挂靠在任何一张工单上的原因。

### 制品

阶段产出物文件：路径 + 内容指纹。Owner 交付时登记新版本，内容快照落盘。评审和人工门绑定的是**当时那一版**的指纹——制品变了，旧结论自动失效。人工门同时绑定评审链指纹（最新评审报告的复合），等待期评审报告变化同样使旧决定失效并重呈新卡。

### 决定

用户拍板的记录：人工门接受或返工、升档审批、追加轮次。一次返工决定会**引发**新一轮返工波——这是「决定 → 波」的因果，而不是时间上的先后。

### 门禁

阶段收尾前的总检查：产出物在场、检查通过、非作者评审在场、核心场景有 Expert 裁决、人工门凭证、路由门（SPEC / E2E 显式判定，skip 必须带可定位依据；仅路由阶段）。门禁没有实体——它每次从事实推导出来。

## 工作模式：波次机的一天

概念钉完之后，看它们怎么一起转。以下是一个单包核心场景阶段的完整节奏：

    produce 波（Owner 写初稿）
    → review 波（Challenger 评）
    → verdict 波（Expert 裁）
    → 若 rework：respond 波（Owner 修）→ 又一轮 review / verdict
    → 全部收敛 → 门禁推导 → 通过 → 进入下一阶段

三个关键机制：

**组合评审等齐。** 多包并行时，各包交付是独立动作——谁先做完谁先交，交付立刻生效（制品登记、快照落盘）。但 Challenger 的组合评审**等当前波内全部派发包交付后才派**——依赖未解锁、尚未派发的包不在等待之列（评审反馈优先于开新范围，DAG 分层解锁后再开下游波）。理由：组合评审审的是「包的组合」——包间接缝、需求偏移、集成风险，部分交付时这份评审不成立。先交的包什么都不亏：它的工作已经安全落盘，后面只是等同伴。

**轮次的真实语义。** 「第几轮」不是数交了多少份报告，而是数这个包经历了几个打磨循环。报告数可以被重复提交污染，循环数不会。

**门禁是波次循环的唯一出口。** 波次机在三种情况下停止派波：没有活跃包了（转门禁）；需用户仲裁（converge-user：轮次耗尽、升级裁决、返工僵局等，等用户决定）；存在未结波在途（wait-inflight：波与波串行，重复推进返回同一在途卡）。然后门禁登场做总检查。波结束不等于阶段结束——阶段要等门禁通过，才流转到下一阶段。

## 底层设计：状态从哪来

这是整个系统最根本的一条：**任务目录就是状态**。没有数据库，没有平行的权威文件。拆开说有三层：

**事实在动作的临界区内同步落盘。** 派发、交付、评审、决定——每个动作发生时，它的事实就写进任务目录，一次原子完成。没有后台补写，没有异步对账。（边界声明：任务目录里的 agents.json 属平台绑定映射——成员会话寻址与模型快照，不参与状态推导；其回填是即发即忘的异步写，失败只降级不阻塞。）

**推导是纯投影。** 「现在在哪个阶段」「该派什么波」「门禁过不过」都不是存储的值，而是每次读取时从事实重算出来的。任何时刻、任何进程，只要读同一个目录，就得出同一个答案。

**教训：事实的粒度必须支撑推导。** 事故暴露的恰恰是这条的反面——波没有稳定身份，幂等、投影、作废都无从锚定；成员挂在一次性派发上，续派必然断链；轮次有两个算法，分叉就是两个状态宇宙。因此我们的建模方向是给这些概念补上实体身份：波有稳定波身份，成员有独立槽位，轮次只有一种算法。其中波身份与轮次算法已落地（轮次唯一算法：每包取已交付报告 round 的最大值，round 由派发事件抄写，成员不填）；成员身份现状为 agents.json 映射 + 倒序回溯的过渡形态，独立槽位（memberSlot）是终局后置项。这不改变「目录即状态」，而是让目录里的事实粒度配得上推导的需要。

## 能力边界与灵活度

现在回答最实际的问题：**用户能分配的最小工作单元是什么？答案是阶段。**

CLI 上用户可显式寻址的最小单位就是阶段：任务从任意阶段介入，运行到该阶段验收即完成。阶段内部走几个轮次，用户不预知、也不预先指定——波次机自主推进（上限三轮），用户以「决定」形式介入的点分两层：**运行期用户卡**（波次推进自动呈卡、等用户拍板）——轮次耗尽卡（追加一轮或结束）、升级裁决卡（挑战者建议升级用户裁决）、人工门卡（接受或返工）、返工僵局卡（接受现状 / 仅重派未修包 / 结束任务）、返工受阻卡（重派或结束）、迁移冲突卡（多版本报告选择保留版本）；**Lead / plan 侧审批卡**（由 Lead 发起或代用户回答）——升档审批卡（批准升档 / 降回默认档）、路由判定卡（SPEC / E2E 显式路由）。两层性质不同，前者随波次推进自动出现，后者不随波次循环产生。

为什么波和轮次不能是分配单位？因为它们**动态、不可预知**：轮次数量取决于挑战者打不打回，开工前无从声明。可分配的单位必须满足「静态、可预先声明」——阶段满足，波和轮次不满足。所以「分配粒度」与「推进粒度」是两套坐标系，这是刻意的设计，不是遗漏。

但边界处有两条已知缺口，我们如实记录：

1. **「只跑一轮」无法表达。** 语义上可行：把轮次预算从策略常量变成任务级参数（一轮后被打回就直接交用户决定）。机制与三轮收敛完全同构，只是尚未开放。
2. **「从某阶段介入并继续走完整个流程」无法表达。** 现状下「介入阶段」与「验收终点」被绑成一个参数：从方案设计介入就只能验收方案设计，想继续走到实施、测试、收尾需要另开新任务。建模上这两个概念应该解耦：起点与终点分开声明。

## 收尾

画出「最小可分配单元 = 阶段」这条线，换来的是一套可以无脑信任的推导：状态永远能从目录重算，门禁永远只检查当前阶段声明的最低输入，成员身份不随工单更替而漂移。灵活度缺口的代价是真实的，但它们是**可列举、可扩展**的——每个缺口都有同构的机制垫在下面，等需要时再开放。

这比「处处灵活、处处不可靠」更接近我们对一个协作运行时的期待：边界清晰，缺口诚实，演进有路。
