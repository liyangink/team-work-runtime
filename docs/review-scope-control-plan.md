# 审查范围与返工收敛修改方案

状态：按用户批准方案实施完成，自检与交叉复核通过；用户随后授权提交和同版本本地安装，安装已完成。真实模型行为待使用验收，版本保持不变。

## 需要批准什么

建议先做一轮小改动：统一各角色收到的验收基线，明确审查意见的处置，再用现有交付和评审链执行。目标是完成用户约定的需求，不是消灭审查期间发现的所有问题。

本次修改角色/场景引导、skill 和派单文本；不新增角色、审查轮次、工具参数、任务状态、人工门或模块。不修改波次机、门禁、报告校验、选模和会话恢复机制，也不开发历史问题的自动登记、排期或治理系统。

关键取舍：先纠正成员判断依据和返工行为，不让 Runtime 自动判断一个问题是否属于需求。代价是每轮派单都带验收基线，文本略有增加；收益是审查者不再缺少完成标准，返工时不只看到新增意见。此版仍依赖成员遵守引导，不承诺机器强制杜绝范围膨胀。

用户需决定：是否批准下文的修改范围及分流规则。批准后实施、自检和一次小范围交叉复核，不默认展开八视角审查；不自动升版、安装、提交、推送或发布。

## 一、为什么这样改

以下是已读取源码的事实，不是拟议实现：

- `runtime-v3/cli.mjs` 的 `dispatchCard` 给包 Owner 注入 `done` 完成标准；Challenger/Expert 的包计划只有包名和交付状态。双方的验收信息不对称。
- 同一函数将目标、约束和排除项放入首次派单与 `promptFull`（断链恢复用的全量正文）；正常续派的 `prompt` 省略这些信息，依赖成员保留原上下文。
- `reworkContext` 只按包归属过滤 Challenger 意见，没有区分必须关闭的阻塞与其他发现。
- `runtime-v3/intake.mjs` 的评审检查要求意见含严重级别和描述；`runtime-v3/waves.mjs` 根据评审结论及意见的包归属选择返工包，不判断本轮必要性。已用非核心场景纯函数夹具验证：相同的返工结论下，`info` 与 `blocker` 都进入回应轮；通过且保留 `risk` 可以继续推进。核心场景仍须既有 Expert 裁决。
- 现有引导已经要求最小改动、不把偏好包装成缺陷、第三轮不重新发散，但没有完整说明真实问题、本轮必要性与开发授权的区别。

因此，优先补上共同基线与处置纪律。不在本次增加结构化问题生命周期、自动复杂度评分或新的批准协议；这些都会扩大工具和状态契约，且提示行为的实际改进尚未验证。

## 二、审查意见如何分流

### 1. 本轮阻塞

只有下列关系成立，才要求本轮关闭：交付不满足已约定的需求或完成条件；本次修改引入回归、违反适用的既有约束；或者某个问题是实现本次目标不可缺少的直接前提。

要求返工时说明：对应哪条需求/完成条件，不修会怎样失败，证据与触发条件是什么，现有保护为何不足，以及最小必要修正。证据可以是代码、接口合同、测试、实测或可核验的失败推演，不强求已经发生事故。

“阻塞”不是“严重问题”的同义词，也不由概率、新旧或文件位置单独决定。历史问题如果直接使本次目标无法成立，可以成为阻塞；低概率但有可信触发链和重大后果，也可能需要处理。

必要测试、正确性修正和满足既定约束的局部调整，通常属于原需求的完成，不一概视为扩展。若必要修正本身越出已授权的产品范围，先请求用户决定，不先实现再补批准。

### 2. 非阻塞建议

不影响约定交付的优化、风格偏好和措辞建议，不作为返工依据。无实质价值的意见可以不报；有价值的建议简要注明“不影响本次验收”，不要求反复打磨。

格式或语义问题若妨碍用户理解关键取舍、改变接口含义或违反明确交付要求，则按实际影响判断，不能一律归为小问题。可以顺手做低成本且不改变行为的修正，但不能因此加开发内容、增加轮次或提高验收要求。

### 3. 范围外发现

与本轮交付无直接必需关系的历史缺陷、治理缺口和额外功能，默认单列，不修、不阻塞当前交付，也不自动开任务、建工单或排期。

只记录值得后续处理的问题，说明证据、影响和为何不属于本次；复用已有报告或摘要，不另造待办系统。独立重大风险可以建议暂停相关上线并请用户决定，但发现风险不等于取得修复授权。

未验证的推断标为待确认，不直接要求开发防护能力。若关系到本次安全交付，先做职责内的针对性查证；证据不足以接受交付时，说明缺什么证据，按现有分歧/升级路径处理，不能机械通过或无限发散。

### 4. 先查已有能力，再要求补建

对监控、权限、恢复、兼容和治理方面的意见，先核对已有实现是否覆盖具体触发条件。未找到不是不存在；存在但不足，应指出缺口。已有能力足够时引用证据关闭问题，不重复建设。

## 三、所有角色使用同一验收基线

### 1. 基线从哪里来

用户原始需求和已批准方案是授权依据。Lead 在现有任务意图中明确本次目标、约束及排除项，必要的方案/需求引用仍通过派单自然语言承载；有包任务的 `done` 只细化原需求，不自行增加功能或验收承诺。

派单生成读取已有 `intent` 和包计划，投影“本轮验收基线”：目标、约束、排除项和当前职责的完成标准。没有包时不臆造 `done`，以任务目标、约束和既有阶段交付合同为准。空约束/排除项不补写猜测值，也不新增必填项。

不新增基线文件或另一份方案。`intent` 修订有记录，不代表修订内容自动获准；Runtime 不解析方案和用户消息证明授权。Lead 必须核对用户批准范围，不能用修改 `intent`、`done` 或可写路径的方式把审查建议变成新需求。

### 2. 派单具体变化

- Owner 只收到本包 `done`；不能把其他包完成标准变成自己的职责。
- Challenger/Expert 收到各包的完成标准、已有交付状态和原有组合职责。未交付包仅用于了解计划，不成为“本轮缺交付”的返工理由。
- 无包任务，各角色收到同一任务目标、约束和排除项；完成条件不明确时先澄清，不由审查者发明理想标准。
- 首次派单、回应轮、复审、重裁及在途重建都带当前基线。正常续派不再省略目标、约束和排除项；基线只出现一次，不重复堆叠原上下文。
- 保留 `prompt`、`promptFull` 和原恢复选择协议。两种正文的验收基线一致，不新增绑定层拼装逻辑。Runtime 仅原样投影已有事实，不自行摘要或截断关键条件。

这些文本在统一的 `dispatchCard` 内生成，终端与 DSH 共用，不各写一套。角色职责和文件授权仍是两回事：能写一个目录，不意味着可以增加目录内的任意功能。

## 四、怎样使用现有报告，不改变工具契约

`recommendation` 是对当前交付的通过/返工/升级结论；`findings` 是评审意见数组，现有 `package` 用于包归属。字段保持原样，不增加机器解析的分类字段或固定文字标签。

引导要求按以下方式提交：

- 要求 `rework` 时，`findings` 只放需要本轮关闭的具体依据，多包注明对应包；非阻塞建议和范围外发现放在同一报告的摘要或已有交付物中，注明不属本轮修复清单。这避免它们的包归属被现有波次机一起当成返工包。
- 通过时可以在 `findings` 保留有价值的风险/信息，并说明处置；有这些记录不要求零意见才能通过。
- 严重级别不能代替本轮关系和修复授权的说明。既有 `info|risk|blocker` 合法值和历史报告继续兼容，不因缺少新文字标注拒绝报告。
- Expert 的返工裁决明确真正要关闭的事项；其他观察分开说明，不借技术裁决增加需求。现有组合返工机制不改。

`reworkContext` 增加简短提醒：以下内容是意见和裁决上下文，不是全部必须修复的清单；Owner 只处理已核验的本轮阻塞，其他发现按分流规则处置。原报告、严重级别和包过滤均保留，不靠关键词删意见，也不自动改写成员结论。

区分两类任务：实施交付自身违反需求，可以返工；审查任务发现产品缺陷，通常应合格地报告缺陷，而不是要求审查 Owner 修产品。审查报告缺少证据、归因错误或遗漏已约定审查内容，仍可以返工。

## 五、返工怎样收敛，扩展怎样决定

Owner 独立核验，不为换取通过全盘接受；以证据修正或反驳。Challenger 复审先核对既有阻塞关闭情况和修改带来的回归，已关闭事项无新证据不重开；第三轮聚焦关闭条件和残余风险。新重大问题仍能提出，但须重新说明证据与本轮关系，不能以“最后一轮”为由忽略。

核心场景的技术分歧沿用 Expert 裁决，不能把成本或范围控制当成强行接受缺陷的理由；Lead 核对授权范围和复核链，不重写技术结论。原三轮上限和人工门保持不变。

如果问题确需增加产品功能、治理能力、兼容承诺或独立历史修复，Lead 先向用户说明：为什么涉及本次、不增加能否按原目标交付、最小扩展及代价、建议本次处理还是另做。用户明确同意后才更新现有意图/方案/包计划；范围外事项保持未实施，用户确认前不自动开新任务。

这不是每条意见一道新人工门：通常建议直接分流；只有确需扩大授权或无法安全继续时请求用户决定。使用普通用户交流和已有交付/分歧通道，不新增卡片类型或暂停协议。涉及已批准制品变化，仍遵守现有指纹重新批准；涉及需求/设计变化，仍遵守现有 SPEC 路由规则，不能用一句“同意修复”绕过。

给用户的返工摘要只说：本轮关闭了哪些阻塞，原需求是否变化，哪些发现留待以后，以及尚需决定的事项。不另增完整审查报告模板或必填章节。

## 七、怎么验证

实施先补公开 CLI 回归，确认现状缺少评审者完成标准和续派基线，再修改统一派单生成。至少覆盖：

1. 单 Owner 与多包：各角色目标、约束和排除一致；Owner 仅本包 `done`，组合评审/裁决拥有相关包标准；未交付包不被误判为遗漏。
2. 首派、回应、复审、重裁、在途重建与 `promptFull`：均有基线，正文不重复；会话映射、波次身份、字段和恢复选择不变。
3. 构造“包 A 有本轮阻塞，包 B 有范围外发现”的报告：按本方案只把 A 的返工依据放入 `findings`，B 的发现保留于摘要；验证只返工 A。通过但保留风险的报告仍能推进。
4. 角色/场景引导包含分流、证据反驳及审查/实施区别；无新增字段、角色、轮次或强制报告章节。项目同名覆盖、引导缺失与原工具合同继续兼容。
5. 既有人工门、裁决新鲜度、选择性返工、只读状态查询、恢复与防重复派发套件不退化。运行专项后跑完整仓库测试，并检查打包包含修改的 skill/guidance。

脚本测试证明基线和规则到达，以及给定报告下机制仍正确；不能证明模型总能判断问题归属，也不能声称工具会拒绝不合规的返工理由。

行为验收用少量定向样例，不再开全面审查：措辞偏好不阻塞、独立历史缺陷不顺带修、已有监控能覆盖则不重复建设、本次真实回归仍阻塞、必要历史依赖先查证、超范围修复先请求用户决定。检查实际报告与修改范围；自动测试通过后，真实模型执行效果仍标为待使用验收。

## 八、兼容与限制

旧任务和报告无需迁移，工具合法参数不变。新增引导及基线只影响此后生成/重建并实际送达的派单，不替换成员已收到的文本；不为让规则生效强行重派在途任务。

项目 `team-work/guidance/` 同名文件会整体覆盖包内条目。保留此语义，提示使用自定义引导的项目核对并合并新规则，不静默覆盖用户文件。角色细则可能被自定义覆盖，但统一派单基线仍按 Runtime 生成。

此版没有自动检查用户授权，也没有自动识别范围外问题。如果真实使用仍出现无依据返工，再基于记录另议同步校验或更明确的报告语义，不在本次预埋问题库、评分器或复杂流程。

## 九、方案复核

作者自检完成；两位非作者分别从需求/范围与源码事实/仓库约束交叉复核，均接受，未发现实施阻塞。复核确认现有报告接口可承载分流，统一派单生成可覆盖各类正文，审查/实施语义及真实重大问题的处理路径没有被削弱。

两路复核均强调：给定报告下的机制验证，不代表模型已能可靠判断需求归属。真实行为效果继续列为实施后的验收项，不把它升级为本轮工具或状态机开发。
