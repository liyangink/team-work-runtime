# TWR 成员汇报、返工额度与意图确认卡设计

**建议批准这套改法：成员在交卷前主动发消息先收到一次自判提示，确需协调时下一步可照常发送；人工返工不占自主额度；用户已明确且无信息差的指令不再确认，真正需要决定时展示固定卡面，不再随卡重复附两段写作规则。** 本文是批准正文，不是实施或安装记录。

| 改动 | 用户和团队会看到什么 | 代价与边界 |
| --- | --- | --- |
| 成员汇报 | 开工告知、途中发现、测试计数和交卷摘要优先收进正式报告；必要答询、纠偏、叫停及阻塞求助仍能发送。 | 发送前一次软提醒；下一 Step 重试即放行，已交卷或守卫异常直接放行。交卷后不重复发消息靠规则引导，不做硬禁。 |
| 轮次额度 | 人工返工后的展示轮号继续递增，但不占自主额度；超出旧上限的包也只需一次授权就能做下一轮。 | Runtime 按阶段、包及已落盘因果计算；不改制品基线、定点返工或人工门。 |
| 意图确认 | 开局和变更都按「AI 有实质推断、擅自纠偏或现实有信息差」决定是否弹卡；用户明确指定目标、范围、模型且无信息差时直接登记。 | 保留现有 `caller-reported` 人工决定信任模型；不引入宿主输入凭证。旧会话换模型冲突仍走专用卡。 |
| 卡面与规则 | 首张要确认的卡完整呈现，后续突出变化；机械卡不套审阅模板，普通简报和真正审批各拿所需短提示。 | 只改呈现投影与规则选取，不改原有 JSON 合同或其他人工门，不新增阻塞式问答。 |

本轮只交本文，由非作者 Challenger 独立评审、Expert 技术裁决后按现有人工门批准；不修改任何产品源码、规则、配置或已安装插件，不打包、不升版。下文的接口、字段和文案均是拟议，实施以批准正文为准。

## 1. 证据与根因

## 2. 成员汇报：一次软提示，不收走发送权

### 2.1 规则与成员提示

Owner、Challenger、Expert 使用同一约定：把开工告知、逐条发现、源码核对、测试计数、交卷预告及交卷后的重复总结留给正式 `deliver/review` 或最终结束语；由[锁定工作流契约](<../runtime-v3/rules.mjs#L354-L369>)给不可覆盖的一句，[公共规则](<../team-work/rules/common/index.md>)补正反例，不按模型维护名单。已有派单正文不重写；新派、续派和全量恢复使用同源约定。改[冷恢复提醒](<../dsh/subagent-session.js#L93-L97>)为「同一 key 已登记则正常结束，不预告、不另发交卷摘要」，宿主正常结项通知照常。

- 需要 Lead 现在处理的范围争议、影响授权或不能继续的阻塞：先停受影响工作，Owner 用 `deliver --outcome blocked`（空路径、保留有效制品），Challenger 用 `review --recommendation escalate`，Expert 按原评审合同用待决类裁决；若等结项会继续越界或贻误处置，也可即时求助并说清影响及请求。Lead 主动问询照常答，不必等交卷。
- [Lead 协作规程](<../skills/team-work-v3/references/dsh-orchestration.md>)改为正常通知到达后先核已登记报告；不因普通播报去轮询。Lead 可随时问进度、补信息、纠偏和叫停，原生能力、调用方向和停止语义均不改。

### 2.2 发送前软引导的状态与接口

推荐复用 [sleep-confirm 的 `aroundExecute`](<../dsh/sleep-confirm.js#L274-L300>)形状：首遇返回「未发送」+ `exec.deferContext`，看到提示后的更晚 Step 可确认发送，异常放行。只借运行机制，不复用 bash 回执或 sleep 的整回合放行策略。候选装配点是 [DSH 插件现有执行钩子](<../dsh/index.js#L34-L42>)；SDK `tools.send_message` 是否穿过该钩子、能否正确取得双方身份、Step 与可恢复回执仍须在隔离 DSH 中验证，不以 bash 钩子等同已实现此能力。本轮仅在内存调用现有守卫，核实 bash 首次/同 Step 未执行、下一 Step 执行一次，现有守卫对模拟 send_message 透传；这不是原生发送钩子实测。

1. **找准方向与本轮。** 只看有在册正式派发的成员发给自己的 Lead；从 `tw-dispatch` 在投递前已校验的映射与宿主父子/路由身份取得发送者、实际收件人及当前 `dispatchKey`，核对这一轮确已生效；若是旧轮仍在运行或收单事实不明，不把下一 key 的状态强套上去。不靠模型、显示名字、正文或单独的会话深度。Lead 发起的问询/补信息/纠偏/叫停、宿主投递和结项通知、普通委派或助手通信一律直通。对于成员答询，提示明确允许回复，不设答询窗口或标记：若在未登记时命中同样的一次提示，可在后续 Step 原样发出，不能连续拦截或要求任何授权；缺上下文/Step 时直接透传。不把这一次提示说成零延迟。
2. **先看当前 key 有效登记。** `tw deliver`/`tw review` 的真正成功是 [同 key 结构化回执](<../runtime-v3/intake.mjs#L440-L449>)（`accepted:true` 与相应 `reportId`，[评审亦然](<../runtime-v3/intake.mjs#L676-L705>)）；同 key 幂等成功、合法 blocked/escalate 也是登记，失败、仅承诺交卷、旧 key 的成功都不是。绑定层可从官方原生 `tw` 执行后的参数和回执缓存正例，并对 CLI 交卷、丢回执、冷恢复以 Runtime 对该已知任务/当前 key 的有效报告只读核验为准（现有 [结项投影](<../runtime-v3/waves.mjs#L311-L325>)以报告事实认定，不以代理已退出认定）。只读同一任务的既有事实，不查所有任务、不让成员轮询；不靠解析 Bash 文本。已登记直接放行；判定失败、身份或来源未知则放行，不误当未登记。
3. **当前 key 确认未登记才提示。** 以「成员会话、实际 Lead、当前 key、turn」暂存一次待自判的 Step，不存消息正文。第一次调用不执行原发送，回可恢复的「未发送」及一次 `deferContext`，同 Step 内预排/并行重试只给短回执，不发送、不当作模型已自判。成员到更晚 Step 再发同一收件人即确认**一次**，可调整措辞；并发只消费这次确认中的一次，下一条新发送不继承全轮白名单。新的正式 key、换 turn、结束/作废或插件释放清掉临时提示，已报告事实由 Runtime 恢复。不得自动重发，也不得伪造 `messageId`；原生输出只允许成功 ID 时以宿主支持的可恢复工具错误承载「未发送」。任何守卫异常按原调用执行一次；真正的原生失败原样返回。

拟议提示：「这条消息还没发。如果只是开工告知、过程进度或交付摘要，继续工作，结束时用 tw deliver/review 一次登记；如果是在答 Lead 的问询，或确有范围争议、阻塞需要立即请 Lead 处理，可在后续 Step 再发一次。」这是行为引导，不决定消息真假，不阻塞交卷或迫使模型等待指定时长；不做全禁、限额、收件后过滤、模型文本分类或替换宿主工具。**已登记后工具直通**，重复交卷通知由规则消减，因此验收不要求交卷后技术上零发送。钩子不可用仍保留规则并如实记「软提示未启用」。

## 3. 轮次额度：序号不变，两类授权分开

### 3.1 计算口径

每个阶段进入实例、每个活动包单独算（单 Owner 用匿名包），保留 `projectRounds` 作为展示轮号和评审核对基准，不改任何报告轮号。不按波次数、评审次数、消息数或墙钟时间算。拟议关系：

```text
R = 该包未作废的 Owner 有效 delivered 最大轮号（原投影）
H = R 以内经有效人工返工授权、确有有效 delivered 的不同轮号数
已用自主额度 = R - H
上限 = max(策略默认额度 + 已生效的历史兼容额度, 当前阶段和包实例仍有效的已批准绝对下限)
```

- 第一次 `rework` 及后续人工确认「整波重派」「仅重派未修包」属于用户授权的工作，不占自主额度。从有效报告回溯到同阶段、同包、同轮的 `dispatched(kind=respond)`、原 `causeDecisionId`，再核实真正签发且已选择的人工返工项及其因果顺序。新派发在原字段之外记录实际授权本次 respond 的决定 ID（首次即原决定；后续填对应重派/未修选择）；一个授权在一个包只抵扣一次有效轮，同一个包的同一轮也只抵扣一次。能用旧签发/决定/派发事件唯一对齐的旧轮可重算；缺失/多义不猜抵扣。
- 在途、未交付、blocked、作废波、Lead 刷新不增加抵扣；同 key 修订、回复、重试不重复增加。同波部分交付只给已有效提交的包计算；保留原 F5 整波作废与有效 blocked/僵局恢复规则。人工门决定和授权锚只对当前阶段进入实例生效，旧阶段返工不注入当前阶段；评审/裁决的新鲜度仍以既有报告、清单和指纹检查为准。
- 历史已生效且没有范围元数据的 `extra-round` 保留旧的任务范围加法（去重）；不把旧数字猜分给各包。新决定绑定**当前阶段和这个工作包的持续实例**，不只绑定包名。包实例取「阶段进入序号 + 包 ID + 当前连续计划合同的起始 seq」：从 [journal 的完整计划事件](<../runtime-v3/cli.mjs#L3798-L3814>)顺序比较每个包的规范合同（模型、可写、验收、依赖）。同 ID 合同变了、删除再加入、A→B→A，均开启新实例；无关包变化、整体次序变化而本包合同不变、相同计划零写均不换实例。单 Owner 是同阶段连续未拆包的匿名实例，拆包或退回单 Owner 不继承另一实例的授权。
- 落盘的绝对下限只在实例匹配时生效；**答完未派发或尚未交付时**，实例替换使其未用授权失效，原决定保留审计，不转给新同名包，也不误撤真正未变包的授权。已用轮仍按原投影，替换不清空计数或改报告；原始人门返工因果也不被改写。计划物化、恢复删包/换包、模型回滚等已有写路径一并使用其已提交的材料化合同；[仅记包名的旧模板事件](<../runtime-v3/cli.mjs#L1697-L1718>)不证明实例延续。如现有写点缺完整合同，补齐同一个既有计划事件，不增分包能力或独立账本；缺证据的旧历史不猜，当前合同清楚后从可核实的快照起点签新授权，损坏的新记录诊断且不给预算。

### 3.2 上限卡怎样签发和单次放行

1. `nextWave` 先找到**本来可派**的待返工包，再对这些包检查已用额度。上限是明确类型（拟议 `kind:round-limit`），不是靠问句或通用 `converge-user` 猜；仍遵守有效 blocked、F5 仲裁、依赖、定点返工及在途守卫。专家要求补证据、方向升级、僵局与按包恢复不是上限，不借本修复改变那些决定的语义。没可派的返工不签上限卡。
2. 签发快照绑定阶段及进入序号、目标包及其实例标识、各包已用/上限/展示轮、待返工报告与制品基线身份、相关计划指纹。提示用户「哪些包仍需再修；追加是每个列出的耗尽包各一次，其他包不给额度；或者结束」。原选择仍是「追加一轮 / 结束任务」，不用用户手填包名或轮数。
3. `decide` 用实际展示卡 ID，在任务锁内重算同一待返工投影（只在计算时略过被答的那张待决卡，不写盘、不越过其他有效前置）。绑定相同才追加：对每个耗尽包及其当时实例登记下限 `max(原上限, 已用自主额度) + 1`，派发前只读重算实例，不只在答卡时验一次。在未耗尽包维持旧上限；常规多包同波仍按照既有 `respond` 集合推进。把授权和消费该卡的决定放入同一次 journal 原子提交，读侧由已提交事实投影，不让先写但未提交的 `decisions.json` 单独加额度。
4. 同卡重显、同 ID 同选项重放均不重复给额度；回执丢失用原 ID 重试。报告或计划真正变更后旧待决卡拒绝追加，标注失效并由写侧按当前事实重签或按原 ID 安全结束，不把旧答复转到新卡。历史未决旧样式若由签发阶段、指纹和当前唯一耗尽返工共同证明仍是同一障碍，则可按原 ID 用新算法落盘，不让用户为格式变化再点；若不能证明，则明确重签、保留旧证据，不复用旧授权。既已批准的额度仅授权工作量，不替任何意图、方案、验收或制品变更背书。

以任务 A 为例：展示轮 7、可证两次人工返工，故自主已用 5、上限 5，点一次变 6，即可派展示第 8 轮。如果历史因果缺失，只能算已用 7、上限 5，一次也把下限补到 8，仍然只允许接下来一轮，不先弹两张补欠账。进入下一轮后再次被要求返工，才可能合法签新上限卡；其他独立待决卡（例如确有意图变化）仍可挡住派发，不冒称审批一次可以越过所有门。

## 4. 意图：只确认 AI 补全和需要对齐的信息差

### 4.1 开局与变更同一判据

按最新人工决定，**首次开局、改模型或分包不是单独的必弹条件**。第一次真正需要确认时用完整首卡；后续用增量。命中以下分流，既有必需的阶段批准、换模型冲突和制品刷新/恢复仍各走各的门，不将意图确认当成其他批准。

| 事实 | 处理 |
| --- | --- |
| 新任务或改动的执行事实均由用户明确指定，或可由既有已授权规则机械得出；目标、范围、实际模型及包计划无歧义，与现状一致 | 在首次推进或当前写路径锁内登记授权，继续，不要求再点一次。用户指定实际模型、无已有会话冲突时也不弹。不因准备命令的日常规范化或不变字段触发卡。 |
| Lead 对目标、范围、模型或拆包作了影响授权的自主判断，或给出用户未选定的候选 | 出卡说明「原话、AI 如何补全及其影响」。例：开局只有宽泛目标，Lead 自定落盘范围、分工或模型，不因是首派默认而当作用户选过；实际实施中已授权范围内的普通技术取舍不升级为意图。 |
| 用户的目标/名称/拼写与已知现状不符、存在歧义或 Lead 拟自主纠偏 | 出卡说明「原话 → 现状及证据 → 建议 → 影响」。不能把近似名称当作用户明确指定；无合理候选则请用户先说清，不默认执行。配置未解析等结构性缺件仍同步报错并给恢复办法，不能签成可批准卡。 |
| 用户已经明确选择实际展示过的卡；或只澄清已授权范围、没有实际变化 | 按原卡 ID 处理或正常继续，不用再写一份新意图。模型变更与已有会话确有冲突时仍用原三选换模型卡；若没有另一项独立意图差异，不在换模型卡前后再问同一件事。确认不了回复所指卡时先澄清，不用最新 ID。 |
| 用户原话只覆盖部分改动、旧答复被挪用、已确认的值又被并发改动 | 缺少覆盖的差异不免卡；若需要确认，整份卡绑定实际拟执行的完整快照，只突出未对齐内容，不把既有授权变相重问。 |

### 4.2 复用调用方报告的授权记录，不改变信任模型

沿用 [`decide` 的 `caller-reported`](<../runtime-v3/cli.mjs#L2581-L2605>)：Lead 对用户的原话、所指范围和选择负责，Runtime 对登记内容、完整指纹和真正派发保持机械一致；**不新增宿主输入凭证、用户事件证明、访问控制或受保护写入口**，DSH 原生工具和终端依旧走同一 Runtime。不能把日志里 `user` 标签或“Lead 说用户同意”解释成密码学可验身份，也不承诺阻挡刻意伪造用户原话的调用方。

1. **Lead 报告语义，Runtime 算差异。** 在现有准备/修订入口复用一项可选参数（拟议 `--user-direction`，值为 JSON `{quote, fields}`；`tw-dispatch` 对直接指定的 `writables` 用等价参数透传）。`quote` 是本次用户原话，`fields` 只指出该原话明确覆盖的业务字段，例如目标、当前阶段的可写范围、某角色模型或某包配置；实际值仍来自本次规范化后的现有命令参数，不让 Lead 手工准备指纹、旧卡快照或填写「无 gap」开关。若只授权部分字段，仅对完全匹配的实际修改保留该来源，未覆盖项不自动过门；目标拼写、别名、配置或会话事实须复用已有精确检查，发现冲突或存在未解决的 `gaps` 时自报原话也不能跳过。涉及含义时由 Lead 按规则判断并说明，不强加自然语言解析器或专用用户指令语法。AI 自己的补全、自动注入、成员转述、无明确信息来源和自由备注不能作为用户新决定。
2. **单一资格计算和登记。** `open/intent/roles/plan` 准备并记来源；首次或下一次 `dispatch-plan` 在任务锁内用实际物化的稳定快照核验所有实质差异是否已由「原有效批准基线 + 本次精确直接授权」覆盖（无旧基线时核验完整首派合同）。对后续命令仍使用同一个计算，而不是闻到字段不同就直接重签。同值零写；明确覆盖且无 gap，将直接授权及其对应的规范化差异、前后指纹和原话登记在现有 journal（拟议操作 `intent-authorized`，来源仍为 `caller-reported`），不虚构一张被接受的卡。只读投影对直接授权保留日志来源及快照指纹，不需要为它填造 decisionId。签卡和直接授权共用同一完整快照入口，`run/gate` 是只读，刷新/恢复仍验本卡自己的范围和指纹，不能用一个来源记录跨卡、跨计划或授权不同值。准备未提交或中断只保留候选、不视为生效；同字段后来变化或改回原值不自动复活过期授权，按当前有效基线重新比较。已提交丢回执重显结果，不以原话再次作用在新基线。
3. **真的有卡就按原 ID 决定。** 保留当前 `decisionId`、实际展示的选项、完整指纹、失效与幂等语义。若用户同一答复选择人工门返工并明确补一条要求，允许在原 `decide` 一并提交同形状方向与实际意图改动（拟议 `--user-direction` 在该分支附 `amend`，复用 `tw intent` 已有字段与校验）。在同一任务锁/日志提交写入返工决定和已授权更新；若同时带需确认的补全，则同次登记待确认差异并挡住下一波，不能先答卡再补一个让并发派发抢跑的参数。不把 `--note`、自由派单文本、无效旧卡或用户选「追加一轮」算作隐式批准，也不静默消费其他未决卡。若当前待决意图本身被随后的明确用户指令完整覆盖，记录新来源并按旧 ID 作废那张不再必要的卡，不替用户冒点「确认」；只覆盖一部分则仍要处理剩余差异。

以「请只改这份文档，用我指定的模型，不拆包」为例：路径、类型和模型都已明确且存在，无旧会话冲突时只登记并派发；如果 Lead 想把路径纠正为一个拼写相近但不同的文件，或改成两个包，则必须把选择交给用户。**防绕过限于本轮授权模型**：不提供裸跳过参数，正常误操作不能靠旧指纹、注释、换入口或扩展派单绕过；对故意伪造原话、冒充真实用户或直接篡改状态不新增认证能力。这是明确的设计取舍，不是实施阻塞。

### 4.3 实际派单的可写范围也要对账

[首派](<../runtime-v3/cli.mjs#L4083-L4095>)只在任务第一次把单 Owner 的声明写入快照；[后续 Owner 派发](<../runtime-v3/cli.mjs#L1902-L1931>)会直接解析当次 `--writable`，[交付校验](<../runtime-v3/intake.mjs#L253-L262>)只管是否匹配已签派单。因此在任务锁内、冻结新正文和落盘 `dispatched` **之前**，对前后端共用的 Runtime 路径比较实际范围；人工门/技术返工、恢复和补派不跳过。已冻结的合法在途单不受后续参数改变。

- 多包以当前授权包计划为上界，单 Owner 用当前阶段已授权的路径和产物类型，首卡/首次明确登记时的 `firstWritable` 是入口阶段初值；后续可用直接授权或确认写入适用于该阶段的范围。新阶段没有可证范围时，不把上一阶段的目录或阶段产物类型当作任意路径授权；已有适用范围就不因换阶段弹卡。
- 按[文件与尾斜杠目录](<../runtime-v3/domain/writable.mjs#L1-L20>)及产物类型检查集合包含，不是字符串重叠。范围内可选已授权的子文件或缩小范围，不二次确认；不能把文件升成父目录、改类型、把兄弟前缀当子目录或通过别名逃逸。`none` 是空集，不免除原产物合同。
- 有越界项不派发：本次原话完整覆盖新增范围且无歧义，用 §4.2 直接登记；AI 选路径、擅自替换或只授权一部分，按本阶段的意图差异签卡。只有确认后的候选再过集合检查；旧任务范围不明时保留已有制品和原合法在途单，不从上一次调度参数倒推用户授权。Lead 主动问询和叫停与此检查无关。

## 5. 卡面：机器生成，表达规则不参与

复用现有 `intake` 结构和冻结正文。签发器从完整快照生成一次 Markdown，保存卡片类型（如 `kind:intent`）、模板版本/全量或增量标识与正文；对外可沿用 `question` 承载这份冻结文本，不再同时附一份同样内容的摘要。签发与答复仍绑定完整 `intakeFingerprint`、真实 `decisionId` 和签发时的 `choices`；模板版本和引导不计入授权指纹，不因改文案重签，也不重渲历史卡。选项号来自账本，不由 Lead 重排。

| 固定模板 | 栏目顺序与内容 |
| --- | --- |
| **任务意图确认（完整卡）** | 标题 + 任务/卡片标识 → 用户原始需求（逐字，补充指令与原始需求分开）→ 目标／约束／排除（含现有风险标记）→ 范围与产出（入口、结束方式、产物、验收）→ 角色模型（Owner、Challenger、Expert 三行恒显，展示真实模型和 effort；未解析不可确认）→ 执行分工（有包逐个列 ID、模型、可写范围、完成标准、依赖；未拆包列单 Owner 模型、当前阶段获授权的可写上界及验收（首卡为首派范围））→ 待对齐的信息差（原话、现状/证据、候选及影响；无则明确写「无待对齐项」，不推断全部事实均已证明）→ 选项及后果。 |
| **任务意图变更确认（增量卡）** | 标题 + 任务/卡片标识 → 变更原因和基准 → 本次变更（按完整卡栏目分组，只列改动，新增/删除/前→后；按包 ID 显示实际字段，不甩 JSON 路径）→ 待对齐的信息差（含相关原话、现状和影响）→ 未变更项（数量及完整基准引用，不重复展示）→ 选项及后果。基准是最近可核验的有效批准快照；若基准包含已直接登记的修订，明确展示「最近确认卡 + 其后已登记的用户补充」，给出有效基准摘要/定位，不将补充重复列为待批准，也不错误声称旧卡 ID 单独代表新快照。保留原 `baseDecisionId/baseFingerprint` 卡锚，另区分有效快照及直达变更定位。如果此前只有直接授权而从未出过确认卡，第一次需要确认时直接用首卡展示当前完整快照，注明只决定新差异；旧卡基准缺失但当前事实可核对时也回退完整卡并写明原因；不把猜测差量当事实。 |

值用安全文本容器或转义输出；原文中的标题、围栏、管道不能变成栏目或选项，实际变化不截短、不折叠，阶段进展不进正文。**不新增纯文本模式，不改 stdout 合同。** [bin 的出口](<../bin/tw.mjs#L10-L16>)默认或显式 JSON 都只输出一个 JSON 文档，原生 `tw` [依赖该回执](<../dsh/tw-tool.js#L19-L40>)；保持结构、退出码和兼容字段。

| 入口 | 固定正文的载体 |
| --- | --- |
| 普通 `tw run`（只读） | stdout 仍是 JSON，没有独立人读通道。单卡冻结正文在 `question`；多卡在 `pendingDecisions/staleDecisions` 对应条目的 `question`。 |
| `tw dispatch-plan`（有或无 `--json`） | 两种 stdout 均为 JSON，从嵌套 `card` 或已有列表/别名取同一冻结正文；未显式 `--json` 时才保留既有 [`human` 数组](<../runtime-v3/cli.mjs#L4054-L4067>)。[停卡行生成器](<../runtime-v3/cli.mjs#L3989-L4002>)只嵌一次固定正文，不再把其中已含的问题或选项拼一遍；`human` 不是另一份 stdout。 |
| DSH 原生 `tw`/`tw-dispatch` | 保留机器 JSON 合同和列表；仅在验证客户端现有用户可见 Markdown 内容块后，才让原生展示直接消费同一冻结正文。若无直显接缝，Lead 可在普通回合原样转呈，但这不算机器验收，也不证明用户实际看到了某张卡（§4.2）。不启用阻塞式问答，避免[已知宿主超时](<runtime-roadmap.md#L179-L181>)。 |

显示只投影一次：优先从核过绑定的有效/失效列表（含嵌套）取卡，补入列表未覆盖的单卡或不同 ID 的候选意图卡，按 `decisionId` 去重；只抄出 journal 未收口项的旧列表别名不等于「仍有效」，不能覆盖已核验的失效状态。同 ID 正文、选项或两份权威状态真有冲突则报损坏，不展示两个可选版本。机器消费者可能读取同一 ID 的不同 JSON 别名，兼容字段不删；去重只针对 `human` 和实际用户卡面，不宣称 JSON 字节只含一份内容。多张独立卡仍各显示一次，各用原 ID 答复。

### 5.1 按场景裁剪自动写作引导

意图卡的模板和文字只由签发器决定，[呈现出口](<../runtime-v3/cli.mjs#L152-L175>)改为先识别结构化卡种、真实门类型/返工方向及当前转换，再选择提示。不能以「正在等待用户」或「阻塞」推断在审阅方案，也不能以标题、文案关键词决定分支。现有输出字段不足时沿既有卡片结构透出所需类型，不引入工作流新状态。

| 场景 | 默认自动注入内容 |
| --- | --- |
| 固定意图首卡、增量卡、完整回退 | **无 `presentation`、零规则/clarity I/O**；按第 5 节固定正文及选项展示。只在工具或技能留一句常驻指路「原样呈现已签正文，收取针对本卡的答复」。 |
| 换模型、轮次上限、例行恢复或机械阻塞 | 不带 clarity。优先使用卡内事实和选项后果，所需恢复指引随卡事实走；普通阻塞只说卡在哪里、保留了什么和用户需要做什么，不套方案审阅。 |
| 新派发成功；实际阶段推进、完成或有变化需要汇报 | 只读本场景精简后的 `lead/dispatch` 或 `lead/progress`。派发讲「谁做什么、等什么」，不复述派单；实际进展讲「结果、可信证据、阻碍和下一步」，重要未决仍说明。普通状态查询、重复在途和已归档回执不带整段，同等需要的恢复建议留在卡内。 |
| 真正的人为方案批准、最终验收，或 Challenger/Expert 需用户作技术取舍 | 只读精简的 `lead/decision` 和一个同源的 clarity 审阅**短段**；讲目前要拿定什么、推荐、证据/未验证和各选项代价。完整清单仍在方案/报告，详情按现有规范链接取用；不叠加公共段，不压没会影响决定的风险。 |

混合待决列表同样按实际卡类处理；意图与机械卡原样，只有真实评审项目适用审阅短段，整次响应最多放一份提示并注明针对哪些非意图项。无法识别的旧卡仍显示原事实、选项与恢复信息，不因未知就塞两段全文。历史待决正文、审批流程、各自指纹和静止语义不改。

### 5.2 规则缩短、去重与唯一输出

- **保留原规范，另外界定自动节选。** 改包内 Lead 三时点默认规则，删除反复说明共同目的的句子，留下各时点动作；复杂方案/验收的完整性要求仍在既有 Lead 总则和规范链接，不把决定点短提示当成压缩制品内容。自动派发/进展/决定默认指引分别以不超过约 120/180/200 字符为验收目标；在[现有 clarity 审阅源](<../skills/clarity-review/references/review-rules.md>)标一段不超过约 160 字符、可独立理解的自动节选（拟议单独标记，仍是同一维护源）；不截断段落或把长文复制到代码。公共与审阅原有必读段、独立技能入口和主动按需阅读保留；本次公共段不自动注入。整份包内默认真审批呈现的正文预算约 360 字符（不含链接和项目真实增量），与 §1 同口径回归，**这是目标而非已测收益**。
- **先选层、再去重。** 在 [resolveLeadRules](<../runtime-v3/rules.mjs#L310-L327>)保持同路径「用户覆盖包内缺省，项目补充追加」、文件稳定排序、旁路副本与缺失回退规则。拼接之前按规范化后的正文精确比较（统一 CRLF、去文件外层空行；不改 Markdown 缩进和行内文字），同名内容完全相同只留一份；确有差异一律保留，先原基线后项目补充，不按相似度删条款。不扩到成员规则或 Lead 总纲的独立选源，本轮也不要求查看用户目录。决定点只在命中该路由时惰性加载审阅短段；缺失/坏标记不给假规则，短诊断或规范指路，不挡流程。
- **一次组装，不重复文本。** `tw` 的公共出口统一组装；原生 `tw-dispatch` 只透传，别再拼一份。JSON/DSH 选定一个既有 `presentation` 位置（普通卡或嵌套停卡，不能两处同时放规则）。未显式 `--json` 的 `dispatch-plan` 把正文写入已有 `human[N]`，对应 `presentation` 只留索引指路，不再复制首段；没有提示时不造占位文本。业务卡面及规则分别选择和去重，规则不写入日志、快照、制品摘要或完成凭证。
