# 上下文与会话

## 最小上下文

- 项目制品和 Runtime 索引是事实源，聊天记录不是。
- Lead 只接收控制面索引：任务状态、当前目标、work item、制品路径、门禁、风险和下一同步点；不注入整个任务目录或成员正文。
- Owner 按 `research`、`implement` 或 `check` Profile 接收分配范围必需的路径索引；挑战者和 Expert 默认使用 `check`，Expert 亲自实施时使用 `implement`。
- 路径摘要只负责定位。成员按需读取原始文件，禁止为了“完整理解”扫描全部任务资产。

## 会话生命周期

一个 work item 对应一个成员会话。Owner、挑战者和 Expert 各自使用独立 work item：

1. 同一 work item 的多轮讨论、修订和复核保持固定成员，并续派原会话；下一轮只发送差异、证据缺口、修正目标和新制品路径。
2. Expert 裁决位在同一阶段收敛循环内保持同一会话，便于追踪问题关闭；跨阶段重新建立 work item，不承诺全任务共用一个 session ID。
3. 只有会话失联、Owner 更换、职责/上下文 Profile 实质改变、上下文污染无法恢复，或用户/Expert 要求独立第二意见时才创建新会话。
4. 新会话从任务索引、原始制品和最新轮次摘要恢复，不复制全部聊天历史。

平台若支持 session resume，必须优先复用；不支持时按 Platform Profile 的降级规则重建。具体工具和映射路径只写在平台增量指南中。

平台若提供成员通知或有界等待能力，Lead 只在明确同步点使用：通知表示“需要收集并核验”，不表示完成或验收通过。等待必须有短超时，用户输入和可继续的 Harness 工作优先；平台事件遗漏时允许低频状态复核，但不得据此复制第二套 Agent 调度器。
