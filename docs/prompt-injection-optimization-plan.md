# Lead 提示词与按需帮助重构方案

> 状态：方案设计，以下“拟”均非已实现。本文是本次方案的完整人工批准正文；本阶段只新增本文，不改运行时代码、Skill、规则或测试。新文档的清单登记留待实施阶段一并处理。

## 一、推荐方案与影响

**建议把常驻提示压成分工和不可误操作的短指引，把每次卡片里的长规则压成按时点的最小提醒；完整操作参数、恢复细节、判断方法和表达规范只在需要时经 `tw -h` / 细分帮助或 Skill 引用读取。** 下文命令均为拟议形式；现有实现尚不支持 `-h`。完整任务事实、确认卡、错误原因和恢复信息不是提示词，不得为了节省上下文截断。

这一调整涉及五处：①缩短系统分工表和两项工具描述，不改变工具名、参数或正式派发机制；②在 CLI 出口按决定、派发、进展保留简短且有针对性的 `presentation`，继续无损合并用户/项目的时点规则，不再每次附加整段明晰规则；③将现有 `tw help` 扩展为可直接使用的总览、逐命令和 Lead 指引，`-h` 与 `--help` 在执行任何业务操作前生效；④收窄 Skill 入口，现有四份 references 按判断场景承载详细材料，Lead 通用规则通过 CLI 内已知包根读取，修复不同安装布局下的断链；⑤保留并测试已有首卡、增量展示和自定义规则，新增帮助与资源分层回归。无需新增状态、角色、审批门、守护进程或兼容性框架。

**要付的代价**：首次遇到复杂操作需要主动查帮助或相应 reference；过于压缩可能让 Lead 遗漏上下文，因此必须保留下面规定的固定防呆、用户可定制规则、卡片完整事实与测试。由于用户自定义规则可以较长，不能承诺所有人的卡片都达到字节目标。旧版已安装 Skill 与新版 CLI 可能混用，必须按第六节逐项诊断；不能以更短提示宣称实际模型一定更可靠。

本次不改变需求授权、任务/阶段/波次推导、三标题成员规则解析、成员派单与冷收单正文、评审/裁决、人工门及确认快照，不修与提示优化无直接必需关系的产品缺陷；不重引入任何旧版资产。本阶段不运行外部真实模型、不联网、不执行实施。本方案如获批准，只授权下文列明的提示与帮助改动；独立新增产品功能或历史问题另行取得用户授权。

## 二、已经核验的基线和证据边界

### 2.1 实测支持什么

- [评测报告](../evals/glm53-latest-eval/results/test-report.md#L5-L14) 是 GLM-5.3 单模型、单次脚本化的**受限观察**：外层工作区可写，安全前置不满足，不能作为隔离通过或普遍模型结论。本次没有重跑。源码 Skill 当前 SHA-256 与报告的被测 17,174 字节正文一致；不因此断言其他当前文件均与被测树相同。
- S1 的首次确认卡、确认前不派发、重签只显示增量与待新确认有真实轨迹；旧卡 ID 拒绝是确定性预检，不是该真实会话实测。S3 有两包并行、三轮真实返工、耗尽后停止等待，但 Expert、汇总包和阶段门未触发；S2/S8 未执行，S5/S7 仅部分观察。见[报告](../evals/glm53-latest-eval/results/test-report.md#L71-L90)和[场景限制](../evals/glm53-latest-eval/results/test-report.md#L92-L126)。这些结果要求保留确认、续派与等待边界，不证明删减提示后行为仍成立。
- S1 的原始事件流中，模型按技能基址读取 Lead README 返回 `FS_NOT_FOUND`，随后仍继续；见[原始事件](../evals/glm53-latest-eval/results/raw/sessions/s1a.jsonl#L9-L19)。S3 先尝试相同错误位置，后从包根搜索并读取；见[会话事实](../evals/glm53-latest-eval/results/raw/session-facts.json#L1134-L1182)。这是实际断链，不只是路径写法偏好。
- [原始评审报告](../evals/glm53-latest-eval/results/raw/task-reports/tide-plan/reports/review-d9-49f7cb.json#L22-L32)中 finding 使用 `packages` 数组；[当前评审校验](../runtime-v3/intake.mjs#L222-L265)对返工时的 `package` 作单个 ID 校验，但未在所读部分拒绝该未知字段。[评测报告](../evals/glm53-latest-eval/results/test-report.md#L158-L165)另有受限复现。逐命令帮助应准确演示单数 `package` 并警示未点名含义，**不能声称提示能修复这个校验缝隙**；是否修产品属于独立工作，不纳入本方案。
- 报告还观察到在途重复推进及宿主引导兜底，见[报告](../evals/glm53-latest-eval/results/test-report.md#L112-L120)。它支持保留“正常在途时等待/异常按卡恢复”的简短提醒，不证明需要在每个条目重复长段。

### 2.2 当前工作区，不是干净版本

已查看工作区状态和 [CLI 实现](../runtime-v3/cli.mjs#L705-L808)：已有未提交改动包括首卡由准备后首次推进签发、完整快照、卡 ID/指纹约束、重签增量与缺失基线回退；[Skill](../skills/team-work-v3/SKILL.md#L22-L34)和相关 references 已有分包、原生工具及实际波次指导；[intake](../runtime-v3/intake.mjs#L241-L265)、store 和多份测试也有未提交修改。另有既有汇报方案和规则内容，要求覆盖认知差、全部具体改动项及原因证据、必要时用准确案例/图说明，见[既有汇报方案](lead-reporting-alignment-plan.md#L7-L12)与[现行进展规则](../team-work/rules/lead/progress/index.md#L1-L9)。实施只能在这些内容上定点修改并保留原意，不能用旧版本覆盖。

本方案与上述前序方案不等于已实施或已批准。前序汇报方案当时按用户要求不改 clarity；本方案因拟取消 Lead 每卡自动带入全文，必须同步修正 clarity 资源中“已经自动带入”的少量 TWR 接线说明，属于避免指引失真的必要配套；独立技能的实质规范、原有必读标记和示例不删不改。现有 [文件清单](file-inventory.json)亦有用户改动，本阶段不写入；实施阶段追加本文及实际新增/迁移路径，不覆盖已有条目。

### 2.3 当前实际装载与规模

[插件装配](../dsh/index.js#L11-L48)注册系统提示、两个工具和三个嵌入技能；[技能注册器](../dsh/skill-embed.js#L25-L49)读取各自 `SKILL.md`，随包的资源基址为对应技能目录；自定义 team-work 路径的基址行为不同。引用文档并不会因此自动变成模型上下文；主动读才送入模型。只凭源码不能证明所有宿主的实际加载顺序或缓存情况。

在本工作区，仅为度量调用了无真实模型的本地纯读取代码：禁用用户规则、未提供项目追加，取包内默认；按 UTF-8 字节统计，路径长度使明晰段结果随安装位置变化。下表不是 token，也不是同一请求必然同时出现的总量：

| 注入或资源 | 当前实测基线 | 拟议默认目标，非验收结果 |
| --- | ---: | ---: |
| 系统提示：未配置档位时 | 1,956 B，含动态 unresolved 提示 | 约 400–800 B；候选从按需 `tw models` 取 |
| `tw-dispatch` 工具描述 | 3,236 B，其中同一决策表 1,569 B 又出现在系统提示 | 约 400–900 B；异常处理留卡片和帮助 |

## 四、拟议接口、字段流转与最小防呆

### 4.1 固定提示与两项工具

以下是**示例措辞，不是已实现输出**；最终字句可编辑但不得弱化列出的条件。

- 系统提示保留：“正式波次由 Lead 用 `tw-dispatch`；普通委派用原生工具，成员按派单交付/评审。新任务先确认，待用户决定时不派发、不轮询、不代答；具体操作查 `tw --help`，缺模型配置不得猜测。”保留普通委派与正式波次的区分、成员身份、意图确认和静止边界。复杂角色模型、原生参数及具体候选移至 `models/roles/plan` 帮助或 reference。取消候选的常驻输出，不更改配置快照、`tw models` 返回或模型选择逻辑。
- `tw` 描述示例：“CLI 参数数组；返回 JSON。总览用 `["--help"]`，命令详情用 `["命令","--help"]`，错误按返回卡处理。”输入 schema 和输出不变。
- `tw-dispatch` 描述示例：“Lead 用于推进并派发正式波次。按卡片行动：等待用户时停下；正常在途等通知；异常按条目恢复，未确认回执先核原会话，勿重复创建。细节用 `tw help tw-dispatch`。”保留 `task/note/writables` 的既有参数说明、目录尾斜杠和输出 schema。不得把 `wait-children` 描述为适用于含失败的批次，也不能把所有 `wait-inflight` 说成只等待。

### 4.2 CLI 帮助：一层接口、无副作用

[当前解析](../runtime-v3/cli.mjs#L3072-L3135)只在命令为 `help` 时返回总表；`-h` 是新的拟议功能。帮助仍由现有 `tw` 工具的 `args` 透传及 [bin 入口](../bin/tw.mjs#L5-L16)共用，不新注册工具，也不要求第二套用户填写的 schema。

| 拟议调用 | 返回与范围 |
| --- | --- |
| `tw help`、`tw -h`、`tw --help` | 总览；保留现有 `ok/commands/notes` 及 18 个命令可发现性，列三种细分入口。 |
| `tw <命令> -h`、`tw <命令> --help`、`tw help <命令>` | 只给该命令用途、必要/可选参数、类型与重复规则、关键结果/拒绝/恢复及脱敏示例；参数事实以现有实现为准。 |
| `tw help tw-dispatch` | DSH 正式派发概览、参数、结果分支、会话恢复以及独立终端替代；按需读取**当前 CLI 包内** DSH reference 并标明来源，不把包内默认文档伪装为当前用户自定义 Skill 的正文，也不把 DSH 实现变成 Runtime 状态。 |
| `tw help lead`；`tw help lead <时点>` | 前者按运行包根读取完整 Lead README；后者接收 decision、dispatch 或 progress，调用现有时点解析器返回当前生效的合并规则及对应详细 reference 入口。 |
| `tw help clarity <范围>` | 范围为 public 或 review，按需运行现有标记提取器并返回原始必读段、完整源的真实包资源定位；public 仅读公共文件，review 按现有 reader 同时读公共与审阅文件；完整文件仍由调用者显式读取。 |

原生调用例子：

```json
{"args":["plan","--help"]}
```

```json
{"args":["help","lead","decision"]}
```

逐命令帮助建议返回 `{ok:true, topic, command, usage, parameters, examples, notes, seeAlso}`；条目只为可读说明而非新校验层。缺资源返回可定位原因和修复指引，不伪造内容，不影响任务事实；未知命令/主题返回现有风格的 `USAGE` 与总览指路。终端人读仍是 CLI 既有 JSON 接口，不以额外文本污染机器结果。各命令至少覆盖：

- `open/intent/plan/roles`：原文、约束与数组、互斥与依赖、模型物化、unresolved；完整分包形状 `[{id,writable:["<路径>:<类型>"],done:["<完成条件>"],dependsOn:["<上游id>"],model?}]`，省略 model 的实际含义与当前实现一致。
- `dispatch-plan/tw-dispatch/run/gate`：推进与只读的区别、目录授权、正常在途和异常恢复、无插件终端投递责任及等待用户的静止约束。
- `decide`：新意图卡传实际展示且被答复的 `decisionId`，歧义先澄清；重签增量只改变呈现，不改变完整指纹；其他卡沿现有约定。
- `deliver`：outcome、summary、paths、checks、unresolved；blocked 留空 paths，越权保留有效制品并升级；已有 `checks` 值及路径验证来自 [intake](../runtime-v3/intake.mjs#L120-L140)。
- `review`：recommendation、findings 每条 `severity/statement`、可选**单数** `package`、Expert 的 verdict 形状及“不点名可能全组返工”；多个包分多条，不把 `packages` 当合法包选择字段。不要将“计划中存在”说成运行时已验证“本次被评审”。
- `models/init/restore/retire/migrate/route/archive/agent-map`：各自输入、是否只读、授权、错误及恢复；其余命令同样不遗漏。

实现入口须在任何会读取或写入任务事实的命令分发之前识别帮助。实现需区分**选项位置的帮助标志**与参数值恰好为 `--help` 的用户原文：不能用全 argv 的简单 `includes` 误拦原文，也不能因带 `--task` 等附加选项而执行真正命令；对未知、歧义或不完整选项先返回用法，零副作用。保留现有命令的入参解析和错误检查权威，不另造与其漂移的输入校验器。

帮助不需要有效模型映射，但绑定层目前先取配置快照（[实现](../dsh/tw-tool.js#L63-L77)）：**仅当取快照抛错**时，在绑定层按精确、短小的帮助调用形状白名单判断是否可继续：`["help"]`、`["-h"]`、`["--help"]`、已知命令加唯一末尾 `-h/--help`、以及本节列出的 `help <已知主题> [已知子主题]`，不得夹带业务参数；符合且 cwd 可确定时，子进程以无配置快照方式执行只读帮助：该帮助专用分支从子进程环境中省略 `TW_DSH_CONFIG`（包括避免继承同名旧值），CLI 在业务分发前再次识别；不能伪造空 tiers 冒充当前配置。**不构造或猜测档位/模型**，帮助内部也不调用选模。其他形状一律沿用原有配置错误返回，不执行子进程：因此快照异常且带额外业务参数的帮助不会执行任务，但也不保证返回帮助。快照正常时，带额外参数的合法帮助仍由 CLI 安全识别并零写入。无法确定 cwd 时沿用原错误，不猜其他项目；此处不对普通业务错误增设 fix 或新校验层。

#### 帮助专用的读取诊断与两条返回通道

现状不能仅靠复用解析器兑现“错误可见”：`listMarkdown` 对目录读取异常静默（[实现](../runtime-v3/rules.mjs#L62-L74)），文件读取失败仅在部分层发 stderr（[实现](../runtime-v3/rules.mjs#L91-L114)）；原生绑定若有 stdout JSON，会选 stdout 而丢弃 stderr（[实现](../dsh/tw-tool.js#L31-L40)）。另外配置快照异常卡当前只有 `code/message`，没有 `fix`（[实现](../dsh/tw-tool.js#L63-L67)）。这不是所有业务拒绝都有完整恢复说明的证据。

拟在现有 `resolveLeadRules` 的目录枚举、规则文件读取和用户根归一化检查处增加**仅供帮助调用选择传入的诊断回调**；未传回调时成员、普通卡片调用的返回数组、排序、空文件、stderr 警告、覆盖/追加及降级行为均不变。帮助调用传入每次独立收集器，随已解析正文返回诊断，不通过全局截取 `console.warn`，不做第二次宽泛扫描，也不保存新状态。收集层、实际访问的路径或已知相对路径、操作（目录枚举/文件读取/根归一化）、错误码、实际降级动作和可执行恢复建议；仅合并相同层、路径、操作与错误码的重复诊断，不删除不同路径或原因。

- 用户/项目**可选文件或目录的 ENOENT** 是正常缺省，空用户文件是有意清空：不误报异常或自动回退；读取/枚举的 EACCES、EPERM、EISDIR 等非 ENOENT 失败则保留已能读取的规则，分别报告用户层回退、项目追加跳过或包内规则不可用。用户根归一化的可选嵌套目录不存在按原语义处理，非 ENOENT 失败记录“归一化探测失败及已采用的降级”，不能假称已读全。
- 对帮助**明确请求的包内 README、明晰资源或 DSH reference**，缺失、不可读或明晰标记损坏均是该帮助资源失败，给出定位、原因及修复安装或权限后重查的建议；不以其他文件冒充。对于时点目录内按现有规则可选的同名包文件，缺失仍可正常回退/追加，不额外设必备默认文件门禁。
- `tw help lead <时点>` 返回拟议形状 `{ok:true, topic:"lead", point, rules, complete, diagnostics:[{layer, path, operation, code, message, fix}]}`。`rules` 使用现有合并后的正文；`complete:false` 表示**本次实际检查出现不可忽略的读取/枚举失败**，有可用正文也不能说完整；`complete:true` 仅表示本次已检查范围内未发现此类失败，不证明其他未查目录无问题。所有可读规则为零但目录按规则均不存在时如实返回空结果，而不是臆造规则。直接请求的必需文档无法读取时返回 `ok:false`、`code/message/fix`；多部分明晰帮助可返回已读部分、`complete:false` 与逐项诊断。对明晰文件沿用 `requiredClarityText` 校验并在帮助读取处捕获真实异常，不解析错误文案来猜状态。
- 诊断和正文**一起作为 JSON 对象写入 stdout**；终端收到同一个结构化卡片，原生 `tw` 正常解析 stdout 后也可见完整诊断，不依赖 stderr。它不改变普通业务调用已有错误形状、不扩修历史配置、超时或 spawn 错误；没有完整修复建议时不声称已有。用户检查权限/安装时保留自定义内容，不自动覆盖、创建或修复配置。

### 4.3 卡片 presentation：先保事实，再压重复

[现有出口](../runtime-v3/cli.mjs#L3166-L3190) 先调用命令，再按卡片形态附加提示；[绑定层](../dsh/tw-dispatch.js#L216-L218)只透传 Lead presentation，成员派单不额外展开。拟保留此数据流：

```text
业务卡（全部结构化字段 + question/progress/reasons/fix）
  → 分类：decision / dispatch / progress / 无需呈现
  → 本时点极短固定防呆 + resolveLeadRules 当前生效正文
  → presentation（保持原 top-level 或 card 内位置）
  → tw 原样返回；tw-dispatch 沿现有路径透传
  → 用户确需细节时：tw help … / Skill 中相应 reference
```

拟定固定防呆分别为：决定点“说明要决定什么和依据；待决不调查、不派发、不轮询、不代答，答复关联实际展示卡”；派发点“简报实际角色及等待事项，正常在途等通知，异常按各项恢复”；进展点“说明完成内容、影响、风险及下一步，不以工具状态代替进展”。实际用户可定制的时点规则仍按现有整文件优先/追加顺序无损附加，哪怕其文字与固定提醒重复；不可做跨调用已读标记、全文哈希缓存、长度截断或跨来源语义去重。固定提醒替代目前不可由用户规则覆盖的明晰长段，不能让用户清空某个自定义时点文件意外删除这几条基本防呆。

包内三个时点默认文件只保留本时点差异，特别是决定/进展中仍明确：方案审批、阶段进展、审查与完成验收的汇报须覆盖**全部具体待改/已改项、各项原因与可定位证据、影响、风险、未验证和待决取舍**；用户未跟过过程时先补认知差；有认知难度时用准确案例、流程或架构图等帮助理解；同因可合并但不能丢不同结论/归属/状态。无新方向无需虚构选择，不能把摘要当完整批准正文。这些不是可因字节数省掉的“长尾”。

时点分类保持当前代码的精确口径：`awaiting-user/blocked` 优先为决定；`transition=dispatch` 为派发；`advance/complete/wait-inflight`、完成/归档/在途 stop 或 status，以及 `run` 的 working+next=dispatch 为进展；`dispatch-plan` 有 waves 时另走派发呈现。勿把 wait-inflight 一律重分类成 dispatch。终态重复查询仍返回可理解的提示，不能靠会话缓存假定用户已读。

去重只针对**同一次输出中框架自己制造的副本**：系统表不再拼入工具描述；正常卡片不再附明晰必读全文；单次派发的公共等待话术只出现一次。人读 `dispatch-plan` 维持 [现有](../runtime-v3/cli.mjs#L3179-L3188) `human[]` 放完整 presentation、原字段留路由的布局，不复制第二份长正文；所有自定义内容和业务事实都原样保留。若已提供 `card.presentation`，维持不重复添加的行为。错误项的专属修复绝不合并掉。

## 五、Skill、References 和 Lead 规则：完整大纲与查找路径

### 5.1 分层和触发条件

| 层级 | 加载条件 | 保留内容 / 指向 |
| --- | --- | --- |
| L0 系统与工具描述 | 工具可用时 | 身份、正式/普通委派、确认/等待、帮助入口；不放动态候选、长流程。 |
| L1 [team-work Skill](../skills/team-work-v3/SKILL.md) | 宿主按需加载技能 | 身份分流；Lead 的目标/授权、入口与拆包判断；最短操作路线；成员遵循派单；四个 reference 的清晰路由。 |
| L2 命令帮助 | 调用相应 `-h` / help | 命令参数、返回与失败恢复；需要完整 Lead 职责时用 `tw help lead`。不得由 `help` 推进任务。 |
| L3 四份 team-work references | 仅遇相应判断/故障主动读取 | 拓扑与收敛、场景与授权、DSH 会话恢复、规则来源/定制分别归各文件；文件不预读或拼入默认系统提示。 |
| L4 Lead 时点卡片 | 只有现有三类时点 | 小段不可误操作提示 + 当前生效的时点规则；不加载明晰全文。 |
| L5 明晰详细规范与示例 | 用户/Lead 确有表达或审阅需要主动查 | 保留实质规范、标记与独立技能；只更正 TWR 是否自动带入的说明，不自动调用完整技能或重复读独立账本。 |

L1 的拟议大纲：

1. **先识别身份**：已分配成员按本包和派单，不开正式团队；限定只读助手不替代正式交付。Lead 不代做成员技术工作。
2. **Lead 判断**：原始需求/已批准方案是范围依据；从用户语义选阶段；可独立验收且写范围互斥才并行，依赖不明先澄清/串行；不预测下一波、不自行改正式模型。详情链接拓扑与场景。
3. **最短操作**：DSH 用原生 `tw` 做准备，用 `tw-dispatch` 推进；无插件终端用 `tw dispatch-plan`。准备 → 首次推进签完整意图卡且不派发 → 用户确认后按实际返回推进；正常在途等待通知，待用户决定静止。出现未决授权争议先停依赖动作并请用户决定。参数查帮助。
4. **卡片与恢复**：首卡完整展示；已确认后的重签看 diff，基线不可用回退完整卡；关联真实展示的卡 ID，歧义先问；异常按卡，不重建会话或替用户决定。复杂流程链接 DSH reference。
5. **按需目录**：列四个 reference 的主题和触发条件，不要求顺序全读；Lead 通用规则改为 `tw help lead`，不能再写模糊相对路径。
6. **成员入口回指**：交付/评审的具体命令查 help，固定职责和三标题规则由派单携带，不引导成员扫描状态目录或另建团队。

### 5.3 四篇 reference 的实际基址与定位

先区分**已实现事实**与拟修正文案：[插件注册](../dsh/skill-embed.js#L33-L45)对随包 team-work 返回技能根作为 `resourceBase`，显式 `skillDir` 则返回 `<skillDir>/references`；[注册测试](../tests/dsh-plugin.test.mjs#L409-L428)验证了两种基址。现有项目文件系统 provider 测试以 clarity-writing 为例返回项目技能根（[测试](../tests/dsh-plugin-e2e.test.mjs#L143-L161)），`tw init` 对 team-work 的目标位于项目技能目录；team-work 项目副本经该 provider 的实际返回本阶段未实测，拟按同目录形态处理并在实施时核验，若返回不同则先修正定位方案，不能当成已验证。因而当前 [Skill 的四条链接](../skills/team-work-v3/SKILL.md#L34-L34)在自定义基址被当作相对资源基址解析时会多一层 `references`；不能只修 Lead README 而保留这四条无条件相对链接。

**拟议方案：不改变注册器当前的基址契约，不改写或覆盖自定义目录。** 在将来重构的包内 Skill 入口用下列明确流程代替四条一律以 `references/` 开头的链接：

1. 取本次 `skill(team-work)` 返回的实际目录型资源基址 `B`，按平台路径规则规范尾部分隔符；不是依据 cwd、包安装位置或模型记忆猜基址。
2. 若 `B` 末级目录名是 `references`，按已核验的显式自定义基址形态令 `R=B`；若 `B` 末级是 `team-work-v3`，按已核验的随包及待验证的项目副本形态令 `R=B/references`。对其他形态、非目录型基址或路径不可确定，标记来源未确定并请求用户/宿主提供实际资源定位，不把任一形式当作通用默认。Windows 与 POSIX 均按路径组件判断，不能只靠字符串拼斜杠。
3. 按需仅读 `R` 下明确列出的一个文件；文件名及锚点由下表选择，锚点用于定位文内章节，不作为文件系统路径的一部分。读取失败或被权限策略拒绝时报告所选路径与原因，保留自定义内容，不静默换成包内默认或扫描其他目录。待修复资源/明确授权后再读；需要该资料才能安全决定时不假装已读。

| 需要解决的问题 | 所选文件名 | 随包或项目技能根为 B 时 | 自定义技能根为 C 时，B 已是 C/references |
| --- | --- | --- | --- |
| 拓扑、依赖、收敛 | `topology-and-cost.md` | `B/references/topology-and-cost.md` | `B/topology-and-cost.md` |
| 验收分流、授权争议、汇报 | `scenarios.md` | `B/references/scenarios.md` | `B/scenarios.md` |
| DSH 派发、会话与恢复 | `dsh-orchestration.md` | `B/references/dsh-orchestration.md` | `B/dsh-orchestration.md` |
| 成员和 Lead 规则来源 | `rules.md` | `B/references/rules.md` | `B/rules.md` |

上表中的 B、C 都是示意变量而非配置值。四篇之间互链按**当前已读 reference 文件所在的 R**解析；将跨技能的明晰绝对/相对猜测改为 `tw help clarity public` 或 `tw help clarity review`，避免假设自定义技能的同级目录内存在根包资源。`tw help tw-dispatch` 是从 CLI 自身包根读取的**包内说明**，不携带选中 Skill 的自定义基址；它可以说明工具契约，但不能静默替代 `R/dsh-orchestration.md` 的用户定制内容。

上述分支写进新的包内 Skill 文本和其四篇引用材料；如果用户将新版入口复制到自定义目录，它能按注册器给出的 `B` 读取同一自定义目录下的四篇内容。已存在的旧版/自行编写 Skill 不自动重写或覆盖，其自己的寻址是否正确不在本方案中冒称修复；发现混版或缺失时报告具体来源和可采取的手动合并/重装方式，由用户决定，不能擅自覆盖。非上述已核验布局的宿主支持范围需实施时核查，不承诺任意目录结构均能自动识别。

### 5.4 Lead README 断链与安装布局

不要只把路径改成 `../../team-work/…`：它可能在随包结构可用，却不能保证 `tw init` 安装到项目的技能副本或自定义 `skillDir` 布局同样可用。CLI 的 `help lead` 从自身模块的包根读取 [Lead README](../team-work/rules/lead/README.md)，与调用者 cwd/技能基址无关；`help lead <时点>` 则复用 [resolveLeadRules](../runtime-v3/rules.mjs#L289-L311)，展示本次可读取的用户优先和项目追加结果；发生读取失败时按第四节返回不完整标记与逐项诊断，不能称为完整结果。README 目前不是时点合并的一部分，继续是包内人读材料；不暗中将它加入每卡或宣称用户层 README 已参与合并。

需要深读时，帮助提供由包根求得的实际资源定位，而非伪造安装绝对路径；独立终端与插件均可用。包内容缺失/不可读时返回资源诊断、当前短防呆仍在、原任务流程不新增门禁；用户按当前安装通道修复后重查。自定义技能与旧副本可能没有新路由，须标记版本混用、保留用户内容并按现有初始化指引处理，不自动覆盖或扩大读取范围。[tw init](../runtime-v3/cli.mjs#L2940-L3034) 当前仅按目标安装、默认保留已有副本；用户公共规则的摘要同步见 [实现](../runtime-v3/cli.mjs#L2827-L2936)：未修改旧默认可更新，用户修改则保留并写旁路。新默认短规则只有相应副本更新或用户自行合并后才生效；没有运行 init 的已有长副本仍可能继续较长，这是兼容代价，不强制自动迁移。

## 六、兼容边界、实施顺序与失败恢复

1. **固定既有工作树作为基线。** 实施者开始前重读本文件引用的当前源码和未提交 diff，保存已有工作，不回滚或覆盖用户改动；若其他工作同时修改同一文件，先协调串行。只就本方案要求的局部文本与帮助接线改动。
2. **先完成按需帮助。** 在现有 CLI 帮助表旁整理各命令文案，识别总览、子命令和 Lead 主题，增加仅帮助启用的读取诊断回调并让诊断进入 JSON，先验证所有帮助路径零任务写入；同步 `tw` 描述。保留业务命令目前已有的错误码、消息和已有 fix，不删除已有恢复边；绑定层部分错误目前仅有 code/message，本次不扩修为统一 fix，也不将它们描述为已有完整指引。
3. **后精简工具描述与系统提示。** 删除一份重复决策表，保留普通/正式工具分工和无猜档；不改 `tw-dispatch` 创建、登记、续派、确认、输出结构和部分失败处理。只在已有 per-item 长文中消除与批级一致的等待描述，检查每种专属恢复仍可见。
4. **精简 presentation 与默认时点文件。** 保持分类、字段位置及人读布局，保留固定小防呆与所有用户/项目时点正文。将明晰全文从常规卡片改为按需查阅；[明晰提取器](../runtime-v3/rules.mjs#L364-L392)、标记和实质规范仍可用，仅同步修正 clarity 文件的 TWR 接线描述。普通业务规则读取失败沿原回退和原有 stderr 行为；新增帮助的诊断按第四节进入结构化结果，不能让缺失说明伪造已读或成为新门禁。
5. **分层 Skill 和 references。** 按第五节重写入口和四篇文件，修正所有新旧交叉引用与安装基址说明；保留用户既有汇报规则和分包变更。不改变成员固定契约、三标题解析、派单全文及冷恢复的整块匹配。
6. **清单、文档和测试。** 更新 [文件清单](file-inventory.json)（包含本文，若实施确有新增/迁移文件也逐项登记）、现行说明与对应测试；原有测试不得简单删除有用约束，要迁至新查阅位置并核对行为。完成后查看完整 diff、运行第七节回归。不要启动新服务器、安装发布或进行外部模型评测。

**必须原样保留的既有确认链**：`open/plan/roles/intent` 首卡前只是准备；首次推进签唯一完整首卡、无成员；完整原文/目标/范围/验收/角色和包模型/首派范围与选项均不丢；确认绑定实际展示的 `decisionId` 与完整快照指纹。已确认后才可按最近已确认快照显示 `intake.diff`（含 `baseDecisionId/baseFingerprint/changes/unchangedFolded/unchangedCount`）；缺失可核验基线的 `diffBaselineUnavailable` 回退完整卡；未确认重签仍完整；答复歧义先澄清。不得让精简 `presentation` 改变 `question/intake/choices/progress` 或锁内决策路径。

**失败与恢复**：帮助资源缺失时保留原卡、短防呆及诊断，修复安装/资源后只重查，不自动改用户规则；用户规则存在但不可读按现有用户层回退、项目层跳过，用户空文件仍是显式覆盖；普通业务警告目前可能仅在 stderr 且被原生绑定丢弃，新增帮助单独通过结构化诊断明确展示，不声称历史业务输出已修复。模型配置读取失败时，仅第四节限定的安全帮助形式可不依赖快照；业务调用仍按现状返回错误代码和消息，部分错误无 fix，不能声称已自动指明恢复，也不在本次扩修。未确认消息是否到达、会话是否持久化或属于谁时，保留原 ID 和映射，按逐项错误核对，不能因文案变短另建或盲目重投。不存在事务性恢复或跨宿主消息恰好一次的新保证。

**帮助读取诊断专项**：用隔离的包内、用户和项目规则根及可注入的文件读取实现，分别模拟目录枚举和文件读取的 EACCES/EPERM/EISDIR、根归一化探测异常、显式 README/明晰资源缺失或标记损坏；模拟用户同名文件不可读但包内可读，以及项目追加不可读但基线可读。核对 `complete:false`、可读正文、精确层/路径/操作/错误码/降级与恢复建议均在结果 JSON，单项失败不得丢其他项；不同失败不互相覆盖。可选目录 ENOENT 和用户有意清空文件不误报，允许的正常覆盖/追加及排序不变。对**同一夹具**分别走 CLI 终端入口和实际原生 `tw` 绑定，断言 stdout JSON 中诊断同样可见，即使 stderr 非空也不丢；不得用捕获进程 stderr 的测试冒充原生模型可见。验证普通业务调用返回字段和现有警告行为无变化，配置异常仍按第四节限定，测试不更改真实用户配置或规则。

6. **派发与恢复**：运行 [派发测试](../tests/dsh-dispatch.test.mjs)及相关会话测试，覆盖新派/在途/部分失败、同父活/冷、异主、不确定、未确认持久化和断链恢复；单项 key、会话、错误和修复指引不丢；成员正文及冷收单严格一致。确认 sleep hook 与引导未变化。
7. **测量与非回归**：用固定合成配置和空自定义规则，分别计算 UTF-8 字节数：系统文本、两工具描述、Skill 正文、三类 presentation、正常批次逐项与总输出；比较第二节基线与目标，记录样本、路径长度、额外 help 调用数和所有超标原因。另用较长用户/项目规则证明内容不被截断，且单独报告其增量。不以字节比例代替真实 token/成本；运行项目相关自动测试及完整套件并记录退出码、跳过项和与原测试基线的差异。必要时检查打包清单与仓库文件清单一致。
8. **真实行为的限制**：本次明确不启动外部真实模型；若未来要比较 Lead 主动查帮助、意图卡展示、返工与等待行为，须另获用户授权、先证明隔离边界并设计同口径前后对照。现有 GLM 样本只能作为现状与风险线索，不能证明本方案已达到模型行为或成本改善。

## 八、验收结论的判定

实施后只有在完整首卡/增量和用户规则不回归、必要防呆仍可达、帮助和故障恢复能独立使用、真实按需读取与适用自动测试通过时，才可报告“结构重构完成”；如果仅节省字节但遗漏自定义规则、完整汇报要求或错误恢复，不算达标。运行结果、跳过项、未经真实模型验证的行为及实际大小必须分开报告。
