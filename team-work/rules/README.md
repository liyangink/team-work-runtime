# 团队规则库（rules）

本目录是成员派单卡的规则来源，也是 Lead 规则的存放处。库根散文件（含本 README）只作库说明，不注入派单。

## 两层架构

成员卡的纪律区由两层拼成，写规则前先分清一句纪律该落在哪一层：

- **包内锁定层（工作流职责）**：成员身份与禁止越权、范围争议时的停手与升级、评审与裁决的新鲜度和工具合同、只读助手的委托边界。这一层不从规则文件读取，也不能被用户目录或项目目录覆盖；本目录不重复写这些内容。
- **可 DIY 层（本目录）**：角色与场景的执行守则——怎么写方案、实施与用例的编码规范、审查的判断口径、交付摘要的写法等。这一层是数据：改文件即改规则，下一次派发生效，不需要改代码。

派单卡上的段落顺序是：卡头 → 本轮验收基线 → 工作流职责（TWR 固定契约）→ 规范 / 红线 / 建议 → 行动与交付。

## 目录约定

```
common/
  index.md        公共通用规则：所有角色、所有场景的成员都会读到
  <场景>.md       场景公共规则：只给该场景的成员，文件名与工作流声明的场景键（teamScene）相同
<角色>/
  README.md       角色通用规则：该角色在所有场景都会读到
  <场景>/         角色场景规则：只给该角色在该场景的成员
lead/
  README.md       Lead 通用推进纪律（只给 Lead 读，不进成员派单）
  dispatch/       派发与在途时点的 Lead 呈现要求
  decision/       决定点时点的 Lead 呈现要求
  progress/       进展与轮次结束时点的 Lead 呈现要求
```

- 成员规则按「角色 → 角色×场景 → 场景公共 → 公共通用」的顺序读取，同一层内按文件名排序。
- 场景公共文件按工作流定义声明的完整场景集合判定：文件名与任一场景键同名的 `common/<场景>.md` 只进该场景的派单，其余 `common/*.md` 进所有派单。新增场景或角色只需放文件，不改代码。
- 角色目录名与派单角色同名（owner、challenger、expert）；场景目录名与阶段声明的 teamScene 同名。没有对应文件就跳过，不影响派发。
- lead/ 下的目录按呈现时点划分，不是研发阶段；lead/ 根级文件与库根散文件都不注入成员派单。

## 合并方式（方式 A）

同一相对路径的正文按三层取用；目录按文件名动态扫描，新建的文件与新建的角色×场景目录自动生效，不需要登记表：

1. 先读用户公共目录 `~/.team-work/rules/` 下的同名文件；该文件不存在时，回退读包内出厂默认 `team-work/rules/` 下的同名文件。
2. 再读当前项目根 `team-work/rules/` 下的同名文件，把正文追加在基线层之后，按同名二级标题合入同一段。
3. 用户改过的文件不会被后续版本覆盖：配置文件摘要比对后，未改动的文件静默更新为新版默认，已改动的保留用户版本，新版默认写到同目录 `<name>.default.md` 供对照合并。

三层都没有的条目不出现在卡上；某一层读取失败按「这一层没有条目」处理——规则是增强，不阻塞派发。

## 三标题约定

会进成员卡的文件用三个二级标题分区，标题下直接写条目：

- `## 规范`：默认必须执行。
- `## 红线`：绝对禁止，任何理由都不能违反。
- `## 建议`：按场景判断采用，不采用不必解释。

三个标题按「规范 → 红线 → 建议」排列，某个标题下没有条目就整段不写；条目不用「严格遵循：」「红线：」「建议：」等前缀自标力度。三个标题以外的正文不注入成员卡；lead/ 下的时点文案不套这三个标题，保持自然段落。
