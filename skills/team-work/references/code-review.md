# 代码 Review

审查视角与成本档位正交。所有视角都必须覆盖；预算只影响由 Junior、Senior 还是 Expert 承担，不能删除视角。可让一名成员承担多个视角，也可按模块拆分，但最终必须由非作者 Senior 或 Expert 复核整体结论。

## 必须覆盖的八个视角

1. **需求与变更摘要**：变更做了什么、是否覆盖用户需求、是否出现范围外行为。
2. **缺陷与安全**：正确性、竞争条件、注入、权限、数据泄露、资源耗尽和破坏性行为。
3. **错误处理**：异常传播、重试边界、超时、降级、清理、可观测性和用户可恢复性。
4. **逻辑推演**：沿关键正常/失败路径模拟状态、数据和控制流，检查边界与不可达假设。
5. **测试覆盖**：需求、回归、边界、失败路径、并发与集成接口是否有有效测试。
6. **类型与不变量**：类型边界、空值、序列化、状态机、数据约束和跨层契约。
7. **规范与合规**：仓库规则、邻近代码风格、API 兼容、许可证、隐私与领域规范。
8. **影响范围**：调用方、配置、迁移、性能、部署、回滚和未显式修改的下游行为。

## 并行审查方式

1. Lead 固定审查范围与比较基线，提供 diff、相关代码、需求和验证方法。
2. 首轮成员独立审查并运行必要验证，不先共享结论。
3. Lead 合并重复问题，区分本次引入、既有问题和归因不确定项。
4. 第二轮只验证高影响或有争议的问题；第三轮由挑战者/专家验证修复和剩余结论。

## Finding 契约

每个可执行问题必须写明：

- **位置**：文件、行或最小代码范围；
- **归因**：本次引入、既有问题或不确定，并说明依据；
- **严重级别**：阻断、高、中、低；
- **置信度**：高、中、低；
- **触发条件**：可以复现该问题的输入或状态；
- **影响**：对用户、数据、兼容性、性能或维护性的后果；
- **证据**：代码路径、测试、日志、规范或最小复现；
- **修复**：最小且可验证的建议；
- **回归测试**：应新增或修改的测试；
- **验证步骤**：确认问题和修复有效的方法。

缺少触发条件或证据的猜测不能作为阻断 finding，可降为待确认风险。

## 降低误报

- 检查问题是否真实位于审查范围以及是否由当前变更引入。
- 搜索调用方、类型和已有测试，不仅凭局部代码推断。
- 能运行最小验证时就运行；不能运行时说明限制并降低置信度。
- 不把纯风格偏好包装成缺陷，不要求与需求无关的大重构。
- 修复后由非原报告作者验证；作者自证只能作为辅助证据。

## 结论

报告列出八个视角的覆盖情况、已确认 findings、待确认风险、验证结果和建议结果。存在阻断/高严重问题或关键视角无证据时建议 `rework`；没有可执行问题且必要验证通过时建议 `pass`。
