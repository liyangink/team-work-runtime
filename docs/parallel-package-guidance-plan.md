# 单任务分包与波次推进方案（讨论稿）

## 建议与范围

建议把 team-work 主技能中的“是否组团”改成一段**单任务分包与波次指引**：复杂任务先找可独立验收、写范围可互斥的部分；按真实依赖形成 Owner 波次；每次对当时已交付组合做非作者 Challenger 审查，核心场景再按波次由非作者 Expert 裁决；汇总包交付后覆盖新的组合。包数按实际工作确定，不固定人数或数量。

本轮只讨论修改主技能及必要的现有契约测试，**不修改真实技能、Runtime、宿主配置或测试，不安装发布、不执行真实生产任务**。早先已登记的跨任务拆解、独立规划文件和跨任务门禁讨论，保留在既有交付记录及本次覆盖前的快照中作为历史，见 [intake.mjs:173–185](../runtime-v3/intake.mjs#L173-L185)；按用户最新决定暂停，不作为本稿的实施或验收内容，也不研究 worktree。

请用户决定：

1. 是否接受第 2 节的主技能短流程，以及将相邻“一个 Owner”和“第三轮必有 Expert”的文字改成与多包、实际场景一致的表述？这只改变引导，不改变角色政策或门禁。
2. 是否接受第 5 节列出的现有机制限制，先以人工核对和异常暂停降低风险？如果要求机器拒绝错误包名、对同轮内容变化强制复审或实现真实写隔离，需要另行批准机制设计，不在本轮实施。
3. 是否在指定智谱 GLM 5.3 路由可用且隔离得到证明后开展第 8 节的单任务演练？本会话精确查询仍被提供方权限拒绝，模型行为和速度尚未实测，不能以其他路线冒充。

## 1. 何时拆包、如何排依赖

现有主技能已要求独立验收且可写范围互斥时拆包，但没有把各波组合审查、包归属、核心裁决和汇总后的再覆盖串起来，见 [SKILL.md:18–26](../skills/team-work-v3/SKILL.md#L18-L26)。建议 Lead 在准备本任务的意图、或阶段开始的合法计划窗口判断：

- 同一任务的几个部分能各自交付、完成标准明确且实际写范围互斥时，优先考虑并行包；一个小而紧耦合的交付、未知依赖或无法确认互斥时，先澄清或保持单 Owner。拆到每包相对完整可验收即可；启动、等待、重复审查和整合开销明显高于收益时不强拆，不按文件数或固定数量划包。
- 每包有唯一 Owner、项目内规范的 writable、具体产物和 done；真实需要等待上游交付才设置 dependsOn，写入下游需要读取的上游路径。只在需要统一产物时设汇总包，并让它独占自己的输出；依赖不能使两个包共享写路径。
- 新任务先签意图确认卡；无在途、状态允许时可在意图确认窗口计划并重签，blocked 恢复须先有用户明确方向与授权，其他待决卡不重拆；最新卡未获确认不派发。包模型显式 model/tier 在计划时解析，省略复用 roles.owner，缺档不猜默认，见 [cli.mjs:2187–2235](../runtime-v3/cli.mjs#L2187-L2235)。

这些是拟议判断，不是 Runtime 对分包质量或收益的自动评估。本任务内的未决授权争议不因一次拆包而自动获批。

## 2. 拟议直接写入主技能的文字

建议替换 [SKILL.md:22](../skills/team-work-v3/SKILL.md#L22) 的“是否组团”条目；以下是拟议正文，非已实施行为（实施时去掉展示用引用符号，保留列表缩进）：

> - **单任务分包与波次（Lead）**：
>
>   1. **判断**：复杂任务先识别可独立验收、能重叠执行且写范围可分离的部分；安全可拆时优先并行，依赖或写边界不清先澄清或单 Owner 串行，协调成本明显不划算时不强拆；不预设包数。
>   2. **计划**：每包明确唯一 Owner、writable（路径:kind，目录保留尾斜杠）、产物和 done；只给必须等待上游交付的包设 dependsOn，并在下游 done 写明要读取的路径。规范路径并核对已知别名，整个计划包括依赖包的写范围均须互斥；共享文件归唯一 Owner，必要时由汇总包写独占最终产物。
>   3. **派发**：按现有合法窗口登记 tw plan、核对包模型并确认最新意图卡；DSH 用 tw-dispatch 推进，终端由调用方投递 dispatch-plan 输出。已在途的同波派单先等待或按返回恢复，不因某一包先交而重复派发下一波。
>   4. **组合挑战**：按实际波次，非作者 Challenger 审当时已交付包的组合及接缝；未交付包只是计划，不作为缺交付的返工依据。rework 的 findings 只放本轮需关闭项，package 必须准确对应本次已交付且被评审的包；未点名时可能全组返工。发现包名不匹配或返工结果与意见不一致，暂停推进，请原评审者按合法通道核验，不由 Lead 改写结论。
>   5. **裁决与汇总**：核心场景按实际波次由非作者 Expert 裁决已交付组合；非核心场景接受后不自动产生 Expert 波。Challenger 的包级返工不等于 Expert rework 能按包选择，后者可能使当前已接受组整体返工。下游/汇总包实际获派后读取已约定的输入；汇总交付后由 Challenger 覆盖新组合，核心场景再按新鲜度规则裁决，保留既有人工门。
>   6. **异常与授权**：已审内容发生变化、输入版本不明、写冲突或授权争议时暂停受影响推进；按现有合法流程完成必要复审、核心重裁和重批，无法确认或没有合法通道则请用户决定。待决用户卡不派发、不轮询、不代答；只读助手不能替代正式成员或审查。

为避免同一主技能相邻语句与多包流程冲突，建议将 [SKILL.md:25](../skills/team-work-v3/SKILL.md#L25) 的“一个 Owner 聚焦改动”改为“各 Owner 聚焦自己的范围”；将 [SKILL.md:26](../skills/team-work-v3/SKILL.md#L26) 的“两轮未收敛 → 第三轮 Expert 裁决”改为：**核心场景按波次裁决，非核心不因轮次自动派 Expert；按场景策略和实际返回推进，默认自主轮次耗尽后交用户决定是否追加**。当前代码中非核心连续三轮返工可直接出用户收敛卡，不能把第三轮 Expert 写成机器保障；若用户希望所有场景第三轮强制 Expert，须另议机制，不能由本次文案修改代替。

## 3. 同一任务内：包、挑战和裁决怎样对应

| 环节 | 已实现的事实 | Lead 的判断与影响 |
| --- | --- | --- |
| 依赖与可写范围 | 计划检查包 ID、模型、完成标准、依赖无环及计划内字符串路径重叠，见 [cli.mjs:2120–2176](../runtime-v3/cli.mjs#L2120-L2176)；依赖就绪的基本条件是上游存在有效交付轮次，见 [waves.mjs:202–219](../runtime-v3/waves.mjs#L202-L219)。 | 依赖不自动提供上游正文/路径，也不解除互斥；实际派下游还受审查、返工和裁决优先级影响，不能说“上游刚交就立刻解锁”。 |
| 同波在途 | 同波部分派单尚无报告时，正常下一派发路径先返回 wait-inflight，见 [waves.mjs:178–193](../runtime-v3/waves.mjs#L178-L193)、[derive.mjs:205–218](../runtime-v3/derive.mjs#L205-L218)。DSH 逐项登记/创建后成员可重叠工作，见 [tw-dispatch.js:415–443](../dsh/tw-dispatch.js#L415-L443)。 | 已交包不必等待另一个包完成工作本身，但下一波常需等全批报告；最慢包和逐项启动影响关键路径，不能保证同时开始。 |
| Challenger 覆盖 | 多包 review 波是一个组合 Challenger 派单，正文要求审当前已交付组合与接缝，未交付包仅为计划，见 [cli.mjs:1046–1073](../runtime-v3/cli.mjs#L1046-L1073)。review 接受时登记该阶段制品组合指纹和各包有效交付轮次快照，见 [intake.mjs:253–266](../runtime-v3/intake.mjs#L253-L266)。 | 不是每个包各开一个 Challenger；其职责是核已交付范围及组合，不因为后续包尚未交付要求它返工。 |
| 按包返工 | Challenger 推荐 rework 时，代码提取所有 findings 的 package；有归属时只将已覆盖且匹配的包加入返工，完全没有归属时将已覆盖的活动交付组纳入返工，见 [waves.mjs:37–39](../runtime-v3/waves.mjs#L37-L39)、[waves.mjs:275–286](../runtime-v3/waves.mjs#L275-L286)。 | findings 仅放本轮必关项，非阻塞观察放摘要/已有产物；核对 package 精确对应当轮已交付、已覆盖包，避免无意扩大或漏掉返工。 |
| Expert 与场景 | 非核心场景 Challenger 接受后可继续下游或门；核心场景对已接受组合由 Expert 裁决，裁决 rework 将当前已接受组加入返工集合，不按 Challenger 的 package 自动精确缩小，见 [waves.mjs:289–302](../runtime-v3/waves.mjs#L289-L302)。是否核心来自场景 policy，见 [default.json:12–20](../team-work/policies/default.json#L12-L20)。 | 专家模型档与 Expert 裁决角色不同；不能因包用 Expert 档就跳过非作者挑战或核心裁决，也不能承诺非核心第三轮自动产生 Expert。 |
| 汇总及门 | 已交付组合的审查、返工及核心裁决优先于新包，见 [waves.mjs:323–355](../runtime-v3/waves.mjs#L323-L355)。后续新交付包未被旧包轮次快照覆盖，会触发组合挑战；核心裁决新鲜度按最后交付时间比较，见 [waves.mjs:240–267](../runtime-v3/waves.mjs#L240-L267)。 | 汇总包的交付改变组合，正常情况下需再挑战、核心场景需新鲜裁决；波次机返回 gate 只是开始当前阶段门禁判断，不等于门已过或人工卡已签。 |

## 4. 示例：两个前置包、按包返工、再汇总

假设一个核心方案设计任务中，接口分析与故障恢复可独立交付，之后需要统一方案。仅是示意，不要求固定三包；省略包级 model/tier 时按现有规则复用 roles.owner。

~~~json
[
  {"id":"api","writable":["parts/api.md:design"],"done":["交付接口与约束分析"],"dependsOn":[]},
  {"id":"recovery","writable":["parts/recovery.md:design"],"done":["交付故障与恢复分析"],"dependsOn":[]},
  {"id":"summary","writable":["parts/result.md:design"],"done":["读取 parts/api.md 和 parts/recovery.md，合并、消除冲突并核对遗漏"],"dependsOn":["api","recovery"]}
]
~~~

下表假设报告按顺序登记且时间戳严格递增、除标出的返工外均接受、无阻塞或并发外部改写；实际遇拒绝、升级或待决卡时以工具返回为准：

| 次序 | 波次及已交付组合 | 结论和下一步 |
| --- | --- | --- |
| 1 | Owner 同波派 api、recovery；api 先交、recovery 尚在途。 | 等待 recovery 的报告，不因 api 先交就启动下一波。 |
| 2 | 两包均交付后，Challenger 审 api 轮 1 + recovery 轮 1 的组合。 | 若本轮必关 finding 的 package=api，recommendation=rework，下一回应波仅派 api；recovery 不因该 finding 重派。 |
| 3 | api 修订为轮 2 后，Challenger 再审当前已交付组合及改动接缝，快照覆盖 api 轮 2、recovery 轮 1。 | 接受后，核心场景由非作者 Expert 裁决当前组合；若其 rework，当前已接受组进入返工集合，不是只按 api 标签重派。 |
| 4 | 核心裁决接受后，summary 获派并只写自己的最终文件。 | summary 交付形成新组合；它不能改前两个包的文件。 |
| 5 | Challenger 审 api 轮 2 + recovery 轮 1 + summary 轮 1 的组合。 | 接受后核心 Expert 对新组合给出新鲜裁决，再进入阶段门禁判断。 |

非核心场景在相同接受路径下跳过第 3、5 步的 Expert 裁决波，仍保留 Challenger 和适用人工门。默认工程工作流中，显式以 design 作为单阶段入口时对应 scoped-final-design 人工验收；运行完整工作流时 design 后进入 design-review，其 design-approval 属于审查阶段。是否签卡、是否过门仍由实际返回决定，见 [engineering.json:6–14](../workflow/definitions/engineering.json#L6-L14)、[gate.mjs:173–202](../runtime-v3/gate.mjs#L173-L202)。

## 5. 必须知道的限制与处理

- **包名填错可能漏返工**：review 接收目前检查 finding 的 severity 和 statement，但未核对 package 是否是当前受审包，见 [intake.mjs:222–231](../runtime-v3/intake.mjs#L222-L231)。若 rework 只点名不存在的包，波次机可能不派任何对应返工包，核心场景转 Expert、非核心场景转下游；本轮纯函数已复现。拟议引导要求在推进前核对真实包名与预期返工集合，发现不一致先停、请原 Challenger 走合法更正；这不是新增机器校验。
- **同轮版本不是强制重审**：Challenger 覆盖按包轮次快照，Expert 新鲜度按交付时间；同 key 的同轮版本变化可能未使旧 Challenger 覆盖失效，磁盘未登记改写也不会自动改变登记指纹，见 [waves.mjs:240–267](../runtime-v3/waves.mjs#L240-L267)、[intake.mjs:143–155](../runtime-v3/intake.mjs#L143-L155)。发现已审版本变化时，不能凭旧接受结论继续；须走合法新版本复审/核心重裁及必要重批，无合法通道则停并请用户决定。
- **登记、评审、批准不是同一个摘要**：Owner 交付回执的单文件 digest 只标识登记内容；reviewedDigest 是当前阶段登记制品集合的组合指纹，人工门还比较按包产物指纹与评审链指纹，见 [intake.mjs:253–271](../runtime-v3/intake.mjs#L253-L271)、[gate.mjs:12–34](../runtime-v3/gate.mjs#L12-L34)、[gate.mjs:39–63](../runtime-v3/gate.mjs#L39-L63)。不得用单文件 digest 直接冒充受审或批准证明；必要版本证据不能合法取得或关联时暂停。只有出现具体风险或必须确认关键输入版本时才核验，不增加每包常态哈希巡检。
- **路径互斥是声明与字符串检查**：计划中 notes/a.md 与 notes/./a.md、notes//a.md 可能指向同一目标但漏判；交付时的路径校验不能阻止之前写入。须规范项目相对路径、核对目录和已知别名/软链，不能确认独占时不并行；这不是操作系统级隔离，见 [cli.mjs:2142–2159](../runtime-v3/cli.mjs#L2142-L2159)、[writable.mjs:13–20](../runtime-v3/domain/writable.mjs#L13-L20)。

## 6. 异常、恢复与速度取舍

部分派发失败时保留已成功项；会话或回执不确定时核对该 key 与既有会话并按返回恢复，不盲目另建或补投。Owner 报告 blocked 不入有效交付轮；当前波次机在无其他可派工作时才给 blocked 静止卡，不能说成员报 blocked 就机械冻结所有工作；若涉及范围/修法授权争议，Lead 应先停依赖动作并请用户决定，见 [waves.mjs:350–368](../runtime-v3/waves.mjs#L350-L368)。用户卡待决时不派发、不轮询、不代答。

restore 只恢复该任务最后登记的指定文件快照；retire 作废未结波并解除在途，不保证终止成员进程，也不恢复未登记工作，见 [cli.mjs:1796–1809](../runtime-v3/cli.mjs#L1796-L1809)。操作前先确认不会覆盖仍在写的工作。自主轮次按 policy 与用户批准的追加轮次计算；耗尽时按实际卡片交用户，不虚构无限续派或自动第三轮 Expert。

并行有机会减少独立工作的墙钟时间，但批次等待最慢成员、逐项建会话、额外组合挑战/核心裁决、汇总和返工可能抵消收益；总模型调用与上下文成本也可能增加。若能量到各成员在波次开始后的启动偏移和持续时间，应取各自“偏移 + 持续时间”的最大值估算该波，不把与成员工作重叠的创建时间重复相加；缺数据只作定性判断。以上是结构推断，真实提速、模型费用和协调开销未实测。

## 7. 验证与拟议实施

**本轮已核验**：只读检查主技能、波次、交付/评审、门禁、派发及相关测试源码；无文件写入地运行纯函数，覆盖示例的按包返工→组合复审→核心裁决→汇总→新组合复审/裁决→gate，以及非核心跳过 Expert、无包归属全组返工、Expert rework 当前接受组返工、包名拼错可漏返工、同轮版本可能不触发新挑战和部分在途等待。另复现非核心三轮持续 rework 后进入用户收敛，而非自动派 Expert。

**尚未验证**：没有运行项目测试、真实生产任务或指定模型演练，纯函数示例不等于真实宿主会话、人工门已签或速度改善。
