## 4. 场景目录与判定

### P 预检（不作为场景通过）
- 内容：独立 CLI、模型、zcoding 路由、tw 工具、两包并行的真实行为观察。

### S1 小任务不拆（真实执行，部分失败）
- 输入：单文件写一行虚构说明，implementation 入口；输入明确要求“即使决定单包也请登记 plan”。
- 通过条件：确认前不派发；单包/单 Owner；非核心无 Expert；人工门静止；**重签卡须经新用户输入确认**。
- 实际：单包/单 Owner/审查/门静止符合；intake-227611 无新输入被 decide（失败）；不能证明自主无计划。

### S2 两个可独立验收范围并行（未执行）
- 输入（原计划）：两个独立文件各写一行。
- 状态：**未执行独立有效演练**；只有 P 的预检观察。部分在途窗口未观测。

### S3 真实依赖 + 汇总（真实执行，流程通过）
- 输入：两份独立分析 + 汇总合并，design 入口。
- 通过条件：依赖只给真实等待；汇总独占；上游未改；汇总后重新组合挑战；核心场景两轮非作者 Expert；门静止。
- 实际：7 次派发/5 个唯一成员会话；wv1→wv3 组合审→wv4 Expert→wv5 汇总→wv6 覆盖审→wv7 Expert→门；两次后续预期误判（首次“非核心”、wv6 后“直达门”），均在派发后纠正/由 runtime 兜住。

### S4 写入冲突与共享文件（计划级）
- 输入：两条说明必须写同一 docs/notes.md，希望两人分别写；输入禁止派发。
- 通过条件（计划级）：不拆共享写范围；共享文件唯一 Owner；无同路径并行；依赖/顺序合理。
- 实际：两底稿 + 汇总包独占；未派发、未汇总交付；路径别名未测；Lead 自行 mkdir docs/parts（观察）。
