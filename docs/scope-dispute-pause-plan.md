## 二、什么争议需要停

分别回答四个问题：缺陷是否真实、是否妨碍原目标、是否本轮必须解决、拟议修法是否获授权。真实缺陷不自动成为本轮工作；与目标有关也不自动授权所有修法。反过来，历史问题或低概率数据/安全风险有可信触发链且直接妨碍目标时，不能以成本或范围名义强迫接受。

先核对原需求/主方案、现有报告、代码或实测证据及已有保护，解决可以用当前事实直接消解的误解。不为争议重新组织大规模调查，不把“先查证”变成继续一轮设计或扩建的理由。若安全前提未知且不能据已有证据排除，保留风险、暂停受影响工作，而不是机械 accept。

下列情况在形成新制品或派修补波前升级：

- 原需求语义或完成条件有不同解释，决定将影响验收结论。
- 双方已核对证据，仍争论某项保证是否为原目标必需，或应本轮处理还是另行处理。
- 要满足某意见需要新增设施、改变原机制/成功含义、扩大承诺或可写授权，尚无明确批准。
- 现有意见声称必须修，但未能说明与原目标的必要关系；Owner 反驳也不能证明可安全按原约定继续。

普通实现细节分歧由原复核链解决，已证明范围内的必要局部修正照常做；无关历史发现按原分流报告、不修、不阻塞、不自动开任务。暂停的是未决授权前提及依赖动作，不预先宣布技术意见无关或某个旧机制安全。

## 三、各角色怎样停

流程详则集中在 scenarios，角色只保留短触发与入口；每项证据和技术结论仍由原作者负责。

| 角色 | 触发与停止动作 | 通过现有渠道交给 Lead |
| --- | --- | --- |
| Owner | 发现需求解释、必要性或修法授权未决，停止依赖该判断的方案修订/业务修改，不先造新增设施或取消既有机制 | deliver blocked，争议说明放 summary/unresolved，paths 留空；引用当前基线、意见和证据，保留原有效制品，不用 delivered 假称完成 |
| Challenger | 核对本版交付时发现上述前提未决，不为促成实现继续要求自动修补，也不以省成本强迫 accept | review 的 recommendation=escalate，保留真实发现/证据及分歧，明确是用户方向问题，不是升模型 |
| Expert | 技术风险必须解决但必要性或修法授权仍未决，不以 rework 授权扩建、不篡改技术结论 | 现有 verdict.outcome=escalate-to-user，rationale/recommendedAction 写前提、证据、备选及待用户判断；recommendation 按真实立场填，不加枚举 |
| Lead | 看到争议报告，或发现新增方向没有可定位授权，在下一次 tw-dispatch/dispatch-plan 前暂停，不派依赖修补波、不自行扩 writable/改目标 | 核对现有基线、报告及用户原句；普通最终消息呈现分歧、当前风险、建议和待确认方向，结束本轮等新输入，不代改成员报告 |

Lead 不必为了取卡先推进一次；即使 Runtime 尚无待决卡，也必须守住上述行为边界。已派在途成员不因普通聊天自动终止或机械冻结，不能声称撤回了已投消息；收到后续争议仍按同一纪律处理，不借本方案新增强制中断或调度器。

用户消息应先说“目前停在什么授权问题、什么尚未实施”，再说明原目标与新要求的差异、证据支持到哪里、不处理的后果、最小可行方向及代价。可以建议按原目标局部修正、明确扩大承诺/设施、或终止受影响工作；这是人读方向选择，不伪装成 Runtime 已有的 choices。无论用户选哪种，未解决的真实安全/数据风险都保持可见。

## 四、等待与恢复不能混同

普通最终消息是在当前工具约束外明确等待方向，不新增权威状态，不等于 Runtime 已签卡或已消费卡。正式 awaiting-user 仍严格静止：不调查、派发、轮询、代答或推进，只有新用户输入恢复。

用户明确方向后，先读现有需求、报告、制品和用户原句，检查是否已有正式待决卡。范围确认不自动变为轮数、升档、阶段接受或部署授权；单纯“继续”无法证明扩展已获准，只有会改变结论的歧义才补问。

| 当前情况 | 沿既有合同恢复 |
| --- | --- |
| Lead 已暂停，但未签卡 | 按明确方向核对授权前提；仅当原派单 key 仍有效、原作者已重核且未变交付仍合格时，可用既有同 key 报告修订重新给结论。Lead 不代改或机械改 accept |
| 已登记评审 escalate，未签正式卡 | 只改 intent 不会解除升级结论；原作者按上述条件重核/修订自己的报告，完成原正常复核。payload 变化按原 ver+1 及当前制品指纹绑定，不能作所有暂停的 accept 捷径。实际需改制品才走原回应轮，不强制追加一轮 |
| Owner produceBlocked/re-scope | 先确认必要性和产品授权，再按现有单包 writable 或多包 plan 通道恢复；非空路径只证明机械条件，不证明授权，不让 Lead 自行扩权 |
| 收敛/其他待决卡已经签发 | 明示用户方向与原卡选择是两件事，聊天不消费卡，不改 choices/grant。按当前卡的实际语义处理，仍需原卡授权时明确请求；不能把 extra-round 写成范围批准或虚构免轮数恢复 |

方向改变时由获授权的原 Owner 更新方案/制品，Lead 将用户明确范围反映到现有 intent/约束/包计划，不以文件路径扩大替代产品授权。已批准正文仍冻结，实质方向变化按原重批；制品或评审链实际指纹变化仍走原人工门。恢复和报告修订不保证旧卡自然消失，遇到现有接口限制如实报告，不发明新 handler。
