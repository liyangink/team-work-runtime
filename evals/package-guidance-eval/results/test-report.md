## 4. 发现

### F1（中高，实际行为）重签意图卡被旧指令代答
- 场景：S1 与 P（P 属预检观察，非独立 S2）。
- 事实：tw plan 触发新卡（intake-227611 / intake-32766e）后，没有新的用户输入，Lead 以旧消息中的“确认 + 先 plan 再派发”作为预授权 decide，随后立即派发。
- 证据：results/confirmation-audit.md；s1b.jsonl:47,50–53,58–59；p2.jsonl:13,16–19,24。
- 影响：新卡内容（逐包模型）未经用户确认即推进。
- 最小建议：**先 plan → 呈现重签卡 → 等待新的用户输入 → 再 decide 与 dispatch**。旧确认或“计划后派发”指令不能代替新卡确认；只把“确认与 plan+派发拆成两个回合”仍可能绕过，必须明确上述顺序。

### F2（低–中，引导相关）S3 两次后续波次误判
- 第一次：turn 1 报告称 design“按非核心场景处理，不自动加 Expert 裁决轮”；实际 policy scenes.design.core=true，运行时派出 wv4 Expert，Lead 在 s3b.jsonl:63 主动纠正。
- 第二次：wv6 覆盖审 accept 后，Lead 在 s3b.jsonl:93 的简报写“accept 则进入 design 阶段门”（暗示直达门）；运行时实际续派 wv7 Expert（s3b.jsonl:101），随后才到门。
- 影响：用户对“接下来还会不会有裁决波”的预期两次偏差；实际执行仍由 runtime 兜住。
- 建议：技能“裁决与汇总”条写明按 workflow 阶段 teamScene 查 scenes[teamScene].core，并说明覆盖审 accept 后核心场景仍需新鲜 Expert 裁决，不能预告“直达门”。

### F3（中，引导相关）DSH 下绕行 bash CLI
- S3/S4：一开始走 bash 调 bin/tw.mjs，读运行时说明并手拼 TW_DSH_CONFIG；S1：先用 tw 工具，两次 plan 参数失败后才转 bash。两条路径不同，不应合并为同一根因。
- 建议：技能 Lead 操作段明确 DSH 宿主内用 tw/tw-dispatch 工具；终端才直接调 CLI 并需调用方提供 TW_DSH_CONFIG。

### F4（低，既有 Runtime）字符串 writable 报错噪声
- cli.mjs:2141–2159 对字符串逐字符迭代，产生“都写 d/o/c”等伪重叠。建议非数组时只报类型错误；本任务不改 Runtime。

### F5（低）Lead 自行预建目录
- S4 中 Lead mkdir -p docs/parts。无害但属 Lead 触碰项目文件系统且未登记。

### F6（低）派发 note 与角色不符
- S3 wv4 Expert 的 note 写“推合并波次”，wv5 汇总包写“裁决通过 推合并包”。

### F7（观察）Challenger 的 CLI 帮助路径
- P 中 tw review --help 不被识别，改用 tw help；既有 CLI 行为。
