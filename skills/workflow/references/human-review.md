# 人工审核

## 配置与硬门禁

从项目 `.team-work/config.yaml` 读取 `humanReview`。每个门禁支持 `required`、`optional`、`disabled`：

- `required`：必须进入 `awaiting-user`，收到用户明确决定并记录证据后才能推进；Lead 不得代答或绕过。
- `optional`：没有发起审核时可推进；一旦发起，必须处理用户决定。
- `disabled`：不发起该人工审核，但仍保留普通制品、测试和验收证据要求。

默认把 `design-approval` 和 `final-acceptance` 设为 `required`。只有用户通过项目配置或明确授权才能降低模式，Agent 不得自行修改配置规避审核。

## 方案批准

在方案团队审查完成、准备进入 SPEC 或实施前发起 `design-approval`。把当前方案文档作为人机对需求、范围和实现方向达成一致的唯一批准基线；代码、SPEC 和测试仍保持各自事实源。

要求方案文档：

- 说人话，使用朴实、精准、简要的表达；不要用内部推理编号、成员代号或未解释缩写增加认知成本。
- 完整说明目标与非目标、现状、所有修改点、影响范围、边界、失败路径、兼容与迁移、风险、验证方式和未决问题。
- 对每项重要变化讲清“当前是什么、准备改什么、为什么、影响什么、如何验证”，不能用概括掩盖遗漏。
- 复杂结构、依赖、流程或时序使用适宜的图或表辅助理解；简单内容不要为了形式增加图表。
- 有重大影响的核心代码设计、核心逻辑或现有实现可附短代码片段，并标明文件位置。代码片段必须来自已经读取的现有代码，贴合代码事实，不得臆造或虚构。
- 尚未实现的代码只能在确有助益时给出，并明确标注为“伪代码”或“建议实现”，不得伪装成当前实现。

向用户只提交一次清晰摘要：方案结论、关键修改点与影响、方案文档链接、仍存分歧和建议，然后提出一个明确问题。用户提出修改时，把反馈交给原 Owner 修订，再经过挑战者和必要 Expert 复核，更新文档后重新请求批准。不要把聊天中的零散结论当作批准。

批准时把方案文档本身注册为 `design-approval` 的证据，使决定绑定当前文件指纹。批准后文档发生变化，原批准失效；返回 `design-review` 并对当前版本重新批准，不得沿用旧结论。

## 最终验收

在实现、测试、代码审查、必要 E2E 及其返工完成后，于任务完成、提交或归档前发起 `final-acceptance`。向用户提供最终交付摘要、可定位代码与制品、验证结果、已关闭问题、残余风险和建议。

把最终交付报告作为决定证据。用户可以批准，也可以指定返工方向：需求或方案偏差回方案，产品代码问题回实施，测试缺口回测试，审查遗漏回代码审查，E2E 制品问题回 E2E。记录用户原意和证据后再流转，不把“继续优化”擅自解释成完成。

## Runtime 交互

1. 用 `task await --gate <gate-id> --evidence-path <reviewed-path>` 把任务置为 `awaiting-user`，将本次提交审核的具体文件固定下来，再直接等待用户普通回复。带 gate 的等待不能用 `task resume` 解除。
2. 用户明确决定后，用 `flow decide --kind human --actor user --status passed|rejected` 记录理由和同一制品证据；Runtime 会拒绝换成另一份文件。不要由 Lead 冒充用户。
3. `passed` 后继续受门禁保护的流转或完成；`rejected` 后按问题归因走返工边或显式 rollback。
4. 若 Runtime 报告批准证据已经变化，回到对应审核点并重新请求用户确认。

人工回复摘要只描述结论、依据、产物、影响、分歧、风险和建议。详细讨论保留在方案、Review 或最终交付制品中。

CoreRuntime 校验等待状态、actor 字段、证据文件和流程，但平台无关 CLI 本身不能证明命令背后一定是人类。`actor=user` 属于可信调用方约定；PlatformPlugin 若能提供可验证的用户事件，应在平台层增强认证。无该能力时，Skill 和 Lead 契约必须禁止 Agent 代填用户决定，不把 Runtime 描述为抵抗恶意调用者的身份认证系统。
