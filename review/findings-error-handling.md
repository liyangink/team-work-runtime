## 发现（已去重归因）

### B1 [blocker] 迁移无原子性/幂等/回滚设计，且与「只增不删」自述冲突

- 位置：方案 §3 F9（L81-85）、§4（L98）、§7（L125）
- 归因：方案自述「全部只增不删、持久化只增字段」，但 F9 补写 `dispatched.detail.waveId` 是**改写既有历史事件**；迁移的中断/重复执行行为完全未定义。
- 触发条件：迁移执行中进程崩溃；迁移工具被重复执行；迁移产物 journal 写入后未校验。
- 影响：半迁移 journal 使 `store.mjs:96` 的 `JSON.parse` 直接抛错（加载路径无容错），任务进入 STATE_CORRUPT 且无恢复边——违反 AGENTS 14「错误必须保留最后有效制品，并可诊断、重试和恢复」；重复迁移还可能重复赋号。
- 证据：`transactions.mjs:16-32` 已具备整文件原子替换原语（temp+rename+sync，可复用），但方案未要求迁移使用备份/校验/幂等；`store.mjs:96` journal 逐行 parse 无损坏容错。
- 最小修复：迁移在 `task.lock` 内执行且明确三步——①先复制 `journal.jsonl.bak` 留档；②全量改写后校验（可解析、waveId 连续性、无重复赋号）；③幂等（已含 waveId 的 dispatched 段跳过，中断重跑不重复赋值）。或者改为**追加** `wave-assigned` 事件、不改写历史 detail，并同步修订 §4/§7 的「只增不删」措辞。二选一后写入方案正文。

### B2 [blocker] F6 重出卡未定义旧未决决定的失效处置——未决卡全链路无指纹对比（机制不可达待修）

- 位置：方案 §3 F6（L63-68）、§5 验收 5（L108）
- 归因：F6 的「指纹过期 → 自动重出卡」在现实现中只存在于**已决定且指纹过期**分支（`gate.mjs:114-121`）；未决卡链路三处均不比对指纹——gate 未结决定分支只出等待卡（`gate.mjs:103-118`）、run 对未决卡原样返回旧卡文本（`cli.mjs:542-556`）、cmdDecide 不校验且取最早未决决定（`cli.mjs:570/584`）。因此等待期修订（ver+1）不会使未决卡失效，「等待期修订必然重新呈卡」按字面实施无法兑现。与组合评审对 requirements 包「F6 部分覆盖（机制不可达待修）」的判定互补：本包提供机制级证据，requirements 包负责覆盖判定行。
- 触发条件：人工门等待期 Expert/Challenger 修订报告（ver+1）后，用户**直接调用 decide 按旧卡作答**（不先 run）；或重出卡后旧未决卡与新卡并存。
- 影响：`cli.mjs:570` 取「最早未决决定」——decide 会把决定绑定到**当前（已变化）的评审链指纹**，而用户拍板的依据是旧卡文本；用户以为批的是旧评审链，实际批准了新评审链。F6 的「决定作用于新评审链」防护被完全绕过，台账 V3-E2E-04 的同源风险（决定与评审链的因果错位）换个形态复现。
- 证据：`gate.mjs:103-118` 未结决定分支只 push「等待用户决定」blocker、不比对指纹（指纹只在 `gate.mjs:114` 已决定分支使用）；`cli.mjs:542-556` await-decision 分支对未决卡原样返回 `issued.detail.reason/choices`、不重算指纹；`cli.mjs:563-598` cmdDecide 无任何指纹对比、`cli.mjs:570` pending 取最早未决决定；`intake.mjs:202-205` 修订注册（ver+1）不会触碰未决决定。
- 最小修复：三选一或组合——①gate 未决分支同样按「签发时指纹 vs 当前指纹」判定，评审链变化即重呈卡；②review 修订落盘时检测「存在未决人工门决定」，将其写入作废事实（如 decided 事件 choice="superseded"），decide 对已作废卡返回 DECISION_STALE 并指引 `tw run` 取新卡；③cmdDecide 入口对未决人工门卡做「签发时指纹 vs 当前指纹」对比，失效即拒绝。方案需明确选择并补验收用例（旧卡直答被拒 + 指引闭环）。

### B3 [blocker] 「归档任务保持只读；重开时再迁移」不可落地

- 位置：方案 §3 F9（L85）
- 归因：与现归档实现冲突：归档删除任务目录、归档 journal 摘要不含 dispatched 事件、CLI 无重开/unarchive 命令。
- 触发条件：任何归档任务尝试「重开再迁移」。
- 影响：方案承诺的迁移路径没有事实可迁、没有入口可触发——按字面实施必须先新建「归档全量 journal 保留 + 重开」能力，本方案未包含；若不实施，该句是误导性承诺，且与「归档只读」边界冲突。
- 证据：`cli.mjs:692-694` journal-summary 只保留 7 类事件、**不含 dispatched/report-accepted**；`cli.mjs:695` `rm` 删除任务目录；`cli.mjs:944-969` helpCard 无 reopen。
- 最小修复：删除「重开时再迁移」承诺，明确「归档任务永不迁移、只读不参与波次推导」（归档本就不做推导，迁移无意义）；若确需未来重开，把「归档全量 journal + reopen」单列为后置项。

### R1 [risk] 部署窗口内未迁移任务的在途守卫失效，可能复现 V3-E2E-01

- 位置：方案 §3 F1（L34-36）、F9、§6 实施顺序 1/3
- 归因：守卫依赖 dispatched.detail.waveId，而 F9 迁移是新代码发布后的独立步骤（实施顺序 3）。
- 触发条件：新代码生效后、迁移执行前，对任何未迁移任务 run（尤其人工门返工在途时）。
- 影响：尾部未交付派发无 waveId，幂等判定无锚点——按 F3 重排后的守卫若只认 waveId，该任务回到「重复派发」旧态（V3-E2E-01 复现）。
- 证据：`derive.mjs:27-44` 现人工门返工分支无守卫（本方案修复对象）；`runtime-v3` 全库 grep 无 waveId/dispatch-superseded 实现（设计阶段，无兼容兜底）。
- 最小修复：守卫对「缺 waveId 的未交付派发」回退旧「尾部连续批次」判定（只读兼容，不写盘）；§5 验收补「未迁移任务 + 新代码」混合态用例；或要求同一发布内先迁移后开放新代码（工具版本门）。

### R2 [risk] 波属性幂等比较缺「阶段 + 决定引用」维度，两个边界会误判

- 位置：方案 §3 F1（L35）
- 归因：比较属性 = kind/role/round/包集，未含阶段与 causeRef；台账 P0-1 曾建议 waveRef 至少含 stage 与 causeRef，方案用全任务唯一 waveId 替代后把属性比较简化了。
- 触发条件 a)：同一波未交付期间用户再次 decide rework（连续两次返工决定），两次派生的 respond 波属性全同；b)：多包波部分交付后，未交付包再派生时包集收缩，与已落盘整波属性不相等。
- 影响：a) 误判为同一未结波，返回第一次返工的旧卡（陈旧返工语境、丢失第二次决定 note）；b) 整波比较失败 → 新开波 → 未交付包被重复派发，违反台账验收门槛 2「多包只等待未交付包，不重复已交付包」。
- 证据：`derive.mjs:27-28` humanRework 现无决定引用；台账 V3-E2E 根因链与验收门槛 2。
- 最小修复：比较维度增加 stage 与 causeRef（最新 rework decisionId）；守卫改为**包级判定**——派生波中每个包若已存在「未交付、未作废」的派发即 wait，而非整波属性相等才 wait。

### R3 [risk] 轮次投影输入口径不一致：§2 建模表 vs F2 正文

- 位置：方案 §2 表 L24 vs §3 F2（L40）
- 归因：§2 表写「每包取关联过的 produce/respond 波的最大**派发 round**」，F2 写「每包 max（交付**报告 round 字段**，按 waveId 去重）」——派发口径会把**未交付**的波计入投影。
- 触发条件：存在未交付派发（在途波、被 retire 的波、成员失联）。
- 影响：零报告包投影轮 > 0 → 依赖满足误判（未交付却解锁依赖）、轮次耗尽误判（一次未交付的 round 3 派发即触发上限）——违反台账验收门槛 4 的「零报告」类必须有确定收敛结果。
- 证据：`waves.mjs:52` 现 roundOf 即报告计数口径；台账验收门槛 4。
- 最小修复：统一为唯一口径「每包已交付报告的 round，按 waveId（缺省回退 dispatchKey）去重取 max」，修订 §2 表措辞为「关联的**已交付**报告」，并补零报告/未交付派发用例。

### R4 [risk] 旧决定的 reviewFingerprint 缺失回退行为未定义

- 位置：方案 §3 F5（L61）、F6（L65-67）
- 归因：F5 只定义了 artifactFingerprint 的旧字段回退（fingerprint），F6 同时对比两个指纹时，升级前签发的决定必然缺 reviewFingerprint。
- 触发条件：升级前已签发/已决定的旧决定在升级后经人工门检查。
- 影响：行为二义：跳过 → 旧决定的评审链变化不重出卡（F6 防护对旧决定失效）；视为不匹配 → 首次检查必重出卡（噪音卡）。
- 证据：`cli.mjs:584` 现决定只写 fingerprint 字段；`gate.mjs:114` 现只比对制品指纹。
- 最小修复：方案明确「旧决定缺 reviewFingerprint → 仅按 artifactFingerprint 判定（旧语义）」，并在重签决定后写入两字段。

### R5 [risk] retire 的非法流转矩阵与 superseded 波的迟到交付语义缺失

- 位置：方案 §3 F3（L49）
- 归因：方案只写了「只允许作废当前未结波，否则拒绝并附恢复指引」，未定义矩阵与迟到事实的消费规则。
- 触发条件：重复 retire 同一波；retire 未知 waveId/已结波/已作废波；被作废波的成员事后用旧 key deliver/review。
- 影响：非法流转行为不可预期（I5 要求拒绝必有出路，需给出每种拒绝的指引）；迟到交付若照常接受，会进入轮次投影/评审覆盖并可能消费门禁；若直接拒绝，成员被卡死（违反无死门）。
- 证据：`intake.mjs:27-29` findDispatch 仅按 key 存在判定，无作废状态检查。
- 最小修复：定义 retire 幂等矩阵（重复 retire 幂等返回 or 拒绝文案 + 指引）；迟到交付**接受为事实**（报告不可变），但投影/门禁消费按「未作废波」过滤，并给出对 Lead 的提示（该交付属已作废波，需重新推进）。

### R6 [risk] waveId 对 Lead 不可见，retire 无寻址依据

### R7 [risk] F7 修订覆盖与模型基线「报告不可变」冲突，旧全文丢失

- 位置：方案 §3 F7（L70-74）、§8 后置项（L130）
- 归因：同 key 修订 ver+1 覆盖同一报告文件，旧版本全文仅剩 journal 的 payloadDigest 链（可审计、不可恢复）；模型基线明文「报告是事实，一经登记就不再改写」。
- 触发条件：成员同 key 改 payload 重交（修订 Challenger/Expert 结论、Owner 修正交付说明）。
- 影响：文档基线自相矛盾；旧结论全文无法追溯（digest 只能证明变过，不能复原内容）；若实现方按模型文档拒绝修订，又与 F7 冲突。
- 证据：`docs/team-work-runtime-model.md` L68；`intake.mjs:130-134/202-205` 现幂等即按「同 key 同 payload 覆盖」实现。
- 最小修复：同步修订模型文档表述为「报告身份 = key+ver；同 key 修订产生新版本，旧版本全文留档后置、digest 链即时可审计」，并在方案正文写明该取舍。

### R8 [risk] 同轮冲突交付无收敛规则，偏离台账 P0-5 建议且未说明理由

- 位置：方案 §3 F9（L83）、§5
- 归因：台账 P0-5 建议「多报告且 digest 不同 → 呈现用户卡选择保留版本」；方案对同轮重复 key（各自成波）的不同 digest 交付无任何收敛机制，同路径制品按最后登记静默覆盖。
- 触发条件：同轮重复派发各交付且内容不同（台账现场正是此形态）。
- 影响：验收门槛 4 的「不同 digest 多报告」类无确定、有裁决的恢复结果；静默「最新覆盖」对用户不透明。
- 证据：台账 V3-E2E-03 处置建议 P0-5；`intake.mjs:151-155` 同路径 items 覆盖。
- 最小修复：二选一——①实现用户选择卡（收敛到唯一保留版本，其余 key 作废）；②方案明确「静默按最后登记生效、历史保留可审计」并回写台账处置说明。不得既不实现也不记录。
