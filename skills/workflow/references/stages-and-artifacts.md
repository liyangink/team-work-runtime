# 阶段与制品

任务可以从下列任意实际研发阶段创建。门禁只检查当前阶段的最低必需输入；表中“典型输出”用于推进和交接，不代表介入当前阶段前必须补齐所有历史制品。

| 阶段 | 目标 | 最低必需输入 | 典型输出 |
|---|---|---|---|
| `research` | 理解需求、项目背景、架构和事实 | `requirement` | 调研记录、代码地图、约束与未知项 |
| `design` | 形成可实施方案并处理分歧 | `requirement` | `design`、决策与风险 |
| `design-review` | 独立审查方案的事实、边界和可行性 | `design` | 评审报告、通过或返工证据 |
| `spec` | 将通过的方案物化为规范与任务 | `design` | `spec`、测试策略、实施拆分 |
| `spec-review` | 交叉检查规范的完整性和可执行性 | `spec` | SPEC 审查报告；局部问题回 SPEC，结构问题回方案 |
| `implementation` | 实现当前范围并保持项目风格 | `requirement` | `source`、实现说明、局部验证证据 |
| `test` | 编写并运行单元与集成测试 | `source` | 测试代码、测试结果、失败诊断 |
| `code-review` | 覆盖全部审查视角并确认修改质量 | `source`、`review-scope` | Review 报告；实现问题回实施，测试问题回测试 |
| `e2e` | 对适用任务用真实路径验证端到端行为 | `source`、`test-scope` | 设计、用例审查、夹具/脚本、实现审查、执行与结果复核证据 |
| `finish` | 汇总实际执行过的阶段并提交 | 无固定历史输入；仍需任务验收 | 收尾摘要、验收证据、提交或交接信息 |

## 项目简介

`research` 涉及项目概况时，先从需求、入口代码、目录、配置、测试和关键调用链提炼一份简洁项目简介，覆盖：项目目标、核心设计、关键模块、关键实现、主要约束、风险与未知项。按理解项目所需的层次组织内容，关键结论附可定位依据；只陈述已经验证的理解，不使用无法验收的身份表述。

## 介入规则

- 已有代码可直接从 `code-review` 创建任务，只注册代码和明确的审查范围；没有设计或 SPEC 不应形成死门。
- 已有设计可直接从 `design-review` 或 `spec` 介入。
- 已有代码但需要补测试，可从 `test` 介入。
- 用户只要求团队讨论方案时，从 `design` 或 `design-review` 介入，按目标是否为“产出”或“审查”选择。
- 从 `code-review` 返工到 `implementation` 前，把已确认 finding 物化为最小修复需求并注册为 `requirement`，避免目标阶段因缺少输入形成死门。其他返工/失败边同样先预检目标阶段最低输入。
- 缺失非必需历史信息时，在风险中说明可能降低判断质量；只有当前行动确实无法继续时才升级为人工门禁。
- E2E 适用性必须判断，但执行可以跳过。用户明确要求或任务存在关键跨系统路径时不可自动跳过；环境不可用时记录 blocker，不能伪造通过。

## 上下文 Profile

- `lead`：任务状态、当前目标、制品索引、决策、风险、工作项摘要。
- `research`：需求、相关代码入口、外部事实问题；默认只读。
- `implement`：已批准目标、专属范围、完成条件、相关代码与规范。
- `check`：审查范围、变更或制品、验收标准；避免注入作者的结论性辩护。

注册时让摘要短而可定位，把完整内容留在制品文件中。关键决策、代码和验证结果必须可回到原文。
