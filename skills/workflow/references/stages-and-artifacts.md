# 阶段与制品

任务可从任意实际研发阶段介入。只关心当前阶段的最低输入；典型输出用于理解目标与交接，不要求补齐历史。

| 阶段 | 目标 | 最低输入 | 典型输出 |
| --- | --- | --- | --- |
| `research` | 理解需求与现状 | `requirement` | 调研记录、代码地图、约束与未知项 |
| `design` | 形成可实施方案 | `requirement` | `design`、风险与决策 |
| `design-review` | 检查方案边界与可行性 | `design` | 评审结论、批准或返工依据 |
| `spec` | 物化规范与任务 | `design` | `spec`、测试策略、实施拆分 |
| `spec-review` | 检查规范完整性 | `spec` | SPEC 审查结论 |
| `implementation` | 完成约定范围 | `requirement` | `source`、局部验证 |
| `test` | 验证行为与回归 | `source` | 测试、结果与失败诊断 |
| `code-review` | 代码审查范围内的质量与影响 | `source`、`review-scope` | Review 报告 |
| `e2e` | 验证真实用户路径 | `source`、`test-scope` | 用例、夹具、执行与结果复核证据 |
| `finish` | 汇总实际交付 | 无固定历史输入 | 收尾摘要与验收依据 |

## 介入与质量提示

- 已有代码可从 `code-review` 介入；已有设计可从 `design-review` 或 `spec` 介入；补测试可从 `test` 介入。
- E2E 必须判断适用性。关键跨系统路径或用户明确要求时不能随意跳过；环境限制要如实说明，不能伪造通过。
- 项目简介应简洁，涵盖项目目标、核心设计、关键模块、关键实现、风险与未知项，并给关键结论可定位依据。
- 摘要用于定位；代码、设计、测试和 Review 的原文仍是事实源。
