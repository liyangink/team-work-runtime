**TWR Multi-Agent Workflow Benchmark Evaluation Report**

**评测环境与数据基准**：15 题 × 9 组全矩阵（共 135 个单元格、195 份独立评测快照），全量在防作弊物理隔离底座下完成实测，所有单元格均自然完赛并完成真实账单与墙钟耗时核算。  
**数据事实源**：[`evals/results/matrix-results.json`](../evals/results/matrix-results.json)

## 一、执行摘要（Executive Summary）

本次基准评测围绕工业级复杂软件工程任务，横向对比了三大阵营共 9 个实验组的真实能力、稳定性和美元成本：
1. **单 Agent 基线（Single-Agent）**：不同智力档位模型（`DeepSeek-Flash`、`GLM-5.3`、`GPT-6.1-Sol` 及单模型天花板 `Claude-Opus-5.5`）在同一会话内的单轮表现（1-Pass）与 3 轮自我反思（3-Pass）；
2. **无协作约束的自由并发多 Agent 团队（Free-Team）**：在缺乏显式状态机与互斥写入约束时，多 Agent 自由交互的表现；
3. **TWR 协作范式团队（TWR Workflows）**：遵循“单一可写 Owner + 非作者 Challenger 强对抗 + 核心场景 Expert 终裁”受门禁强约束的结构化工作流（标准组 `J+S+E`、高配组 `S+S+E`、无裁决极速组 `J+S`、降档组 `J+J+E`）。

### 核心结论速览

- **综合最优解——TWR J+S+E 标准组（Flash + GLM-5.3 + Sol）**：
  全矩阵终版均分 **99.3**（位列全场第 2），在代码实现与困难工程题上均斩获 **100.0 双满分**；15 题真实总成本仅 **$10.971**（题均 $0.731）。在质量逼近最强单模型的同时，**成本仅为其 1/6**，展现出卓越的工程性价比。
- **单模型质量天花板的极端代价——Single-Opus-5.5**：
  终版均分 **99.5**（全场第 1），在超难系统题中展现出极强的深层时序推导能力；但 15 题总成本高达 **$65.928**（题均 $4.395），**单组独占全矩阵总成本的 37.0%**。其高分依赖超高单价与放宽超时窗口后的多轮重试，本质是高昂的算力堆叠。
- **角色档位的智力刚性——TWR J+J+E 降档未能兑现优势**：
  将审查员 Challenger 由 Senior 降为 Junior 后，均分降至 **97.2**（全场第 5，超难层垫底），题均成本反而上升至 **$0.941**。实测表明，在面对非显式架构契约与深层竞态时，审查员存在能力盲区，单次 Expert 终裁无法在有限上下文中完全挽回前序漏检。
- **无门禁多 Agent 的结构性隐患——Free-Team（无主并发团队）**：
  在缺乏互斥文件锁与明确阶段责任边界时，Free-Team 出现多 Agent 并发写入同一文件互相物理覆盖（单项仅得 60 分），均分停在 **95.1**，证实了工程协作必须由状态机与门禁提供底座保障。
- **审查假阳性的决定性纠错——Expert 终裁价值**：
  在无缺陷 Clean PR 审查（`astropy-3824`）中，Single-Flash、Single-Sol 与无裁决组 TWR J+S 均因吹毛求疵产生假阳性误报（仅得 40 分）；而包含 Expert 终裁的 TWR 团队均精准驳回误报，拿下 100 分。

## 二、专有名词、模型代号与评测指标说明

为方便外部受众客观阅读，本报告所涉及的模型代号、评测协议与工作流专有名词定义如下：

### 1. 模型代号与对应智力档位（Model Mapping）
| 报告简称 | 对应真实底层模型 | 评测分配档位（Tier） | 角色定位与工程特征 |
| :--- | :--- | :---: | :--- |
| **Flash** | `deepseek-flash` | **Junior（基础档）** | 极高吞吐量、极低单价，适合高频编写、基础代码生成与只读探索 |
| **GLM / GLM-5.3** | `glm-5.3` | **Senior（主力档）** | 推理深度、上下文理解与成本高度平衡，适合复杂逻辑开发与代码对抗审查 |
| **Sol / GPT-6.1-Sol** | `gpt-6.1-sol` | **Expert（专家档）** | 极强长链逻辑推理与复杂算法推导能力，单价较高，适合核心架构仲裁与疑难决策 |
| **Opus / Opus-5.5** | `claude-opus-5-5` | **Ceiling（天花板对照）** | 业界顶级单模型能力与超高单价代表，作为单模型堆算力与质量上限的对照锚点 |

### 2. 评测协议与核心指标解释（Protocols & Metrics）
- **1-Pass（首答/单轮基线）**：
  模型接收原始任务说明与约束后，直接生成并提交的代码答卷，评估模型在零人工干预下的日常一次性交付质量；
- **3-Pass（自审终答/自省上限）**：
  单模型多轮自迭代模式。模型完成首答后，在同一会话中由系统自动追加 2 轮标准的“请自我审查并修复潜在缺陷”指令（Pass 2 与 Pass 3），以检验单模型在没有外部提示的前提下能否通过自我反思突破认知盲区；
- **ΔQ（过程净增益，Process Delta Quality）**：
  从首交到终版的得分变化量（`终版得分 - 首答得分`）。正值代表通过反思或多角色审查修复了盲区缺陷，负值代表“改坏了原本正确的代码”（自我认知漂移）；
- **自然完赛（Completed-Natural）**：
  受测 Agent 进程在放宽后的时限内未被操作系统或评测沙箱强杀，自然执行完毕退出并产出合法可判分制品。

### 3. TWR 团队角色与核心机制（TWR Workflow Terminology）
- **Lead（主管/Root 会话）**：多智能体团队协调者，负责任务拆包、阶段流转推进与硬性门禁把关，负责编排与推进而不亲自写业务代码。其全部决策产生的 Token 费用均 **100% 计入团队总成本**；
- **Owner（唯一可写负责人）**：当前阶段独占工作区修改权的实现者，物理杜绝多 Agent 无序并发改写导致的代码覆写事故；
- **Challenger（非作者审查员）**：只读角色，必须由非作者独立承担。主动从设计模式、极端边界、成本与推理链找漏洞发起挑战；
- **Expert（技术裁决专家）**：核心场景门禁前必经的技术内容终裁者。独立核验方案完整性、防范审查合谋，并在产生技术分歧时行使最高裁判权；其技术裁决是阶段流转门禁的硬性前置条件；
- **门禁（Gate）**：阶段流转的强制检查点，要求“制品在场 + 自动化测试通过 + 非作者审查通过 + 核心场景 Expert 终裁通过”，杜绝带病交付。

## 三、评测基准的权威性与公平公正性保障

为确保评测结论在学术与工业界均具备绝对的公信力，本评测体系建立了严密的任务矩阵、物理级运行隔离、全口径计费和标准化的自然完赛判定。

### 1. 题库真实性与权威性
评测任务严格取材于当前工业界公认的高难度、真实工程基准（Multi-SWE-bench、SWE-Lancer-Diamond、DevBench、SWR-Bench），共 15 道具有代表性的实际代码问题：
- **拒绝玩具代码**：涵盖真实开源仓库（Django、Astropy、Axios、React Hook Form、Jinja2 等）的历史复杂 Issue 与架构重构任务；
- **全闭环验收**：每道题均配备完备的隐藏测试集、确定性探针与架构约束校验，不仅评估代码能否运行，更检验架构设计是否符合不变量契约。

### 2. 三维立体矩阵：三大任务类型 × 三大难度分层
拒绝将所有题目混排计算单一总分。本评测建立三维正交矩阵，彻底暴露模型在不同能力维度上的真实短板：
- **三大考察类别**：
  1. **代码实现与多特性协同工程（6 题）**：单仓代码精细修改、多特性并行收敛与扩展约束满足；
  2. **架构方案选优与深层竞态根因（5 题）**：候选方案设计决策、深层异步竞态与隐式契约挖掘；
  3. **代码/方案缺陷审查与治理边界（4 题）**：复杂补丁安全性审查、Clean PR 假阳性控制与代码规范约束。
- **三大难度梯度**：
  - **常规题（Baseline，6 题）**：基础缺陷修复与标准规范遵守；
  - **困难题（Hard，6 题）**：深层嵌套逻辑、复杂状态机与竞态消解；
  - **超难题（Ultra-Hard，3 题）**：包含跨层事件穿透路由（`uh2`）、离线乐观操作反弹回滚（`uh1`）、分布式三方事务流水线（`uh3`）等工业级极限场景。

### 3. 事前物理级防作弊与环境隔离
任何模型若能通过外网拉取参考答案或利用包管理器下载预编译轮子，基准均将失去公正性。评测框架在底层执行了严苛的物理级防御：
- **Socket 级网络拦截**：在受测环境中通过底层 `sitecustomize.py` 拦截 Python 的 `socket.connect`、`getaddrinfo` 等 API，任何编程式网络请求直接触发 `OSError` 物理阻断；
- **Git 远程命令包装桩**：对所有 git 操作注入拦截桩，严格禁止 `git clone`、`git pull`、`git fetch` 等外部同步命令，仅放行本地版本库操作；
- **离线包管理器沙箱**：强制注入 `PIP_NO_INDEX=1`、`NPM_CONFIG_OFFLINE=true`，彻底切断外部依赖在线安装渠道；
- **全量执行日志审计**：对数万条执行轨迹进行逃逸正则审计，确保所有试卷均为沙箱内自主探索推导，零参考答案泄漏。

### 4. 全口径真实账单与物理墙钟核算
- **精确到每个 Token**：严格按照各模型官方计费规则（区分未命中输入、缓存命中、缓存写入、思维链输出与峰谷费率）计算每一轮工具交互与生成的费用；
- **全生命周期全口径计费**：**TWR 协作团队的成本不仅包含所有协作者子会话（Owner、Challenger、Expert），还 100% 包含了 Lead（Root 决策推进与门禁判定会话）的全部开销**，不隐藏任何间接管理成本；单模型组亦完整计入 3-Pass 连续会话的全部累计支出。

### 5. 严格的自然完赛基线
所有计入能力分析的试卷快照，均以“进程自然退出、收到最终交付事件并生成可复算交付物”为准（`completed-natural`），坚决剔除中途强杀残卷，确保对比基于模型的真实能力上限。

## 六、关键技术发现与归因深度剖析

### 1. 结构化协作 vs 单模型算力堆叠
- **Opus-5.5 达到 99.5 的真实机制**：
  Opus-5.5 的高分并不是一次做对。在 `nested_projection` 与 `reading_estimator` 题中，由于模型较重且单价高昂，首轮均因超时被截断（首答仅得 10 分纪律分），完全依靠放宽逐轮上限追加多轮自审续跑才拉至满分。这一机制导致其总成本突破 $65，在企业规模化落地中极难负担；
- **TWR 协作范式的低成本满分路径**：
  TWR 标准组（C1）将低廉的高吞吐模型（Flash）作为唯一可写 Owner 承担全量实现；将 Senior 模型（GLM-5.3）作为 Challenger 承担多轮破坏性对抗审查；在进入门禁前，必经由 Expert（Sol）执行一次独立的权威技术终裁。由于高单价的 Expert 仅在终审门禁前单波介入、不被拖入前序多轮试错，团队以极低的 Expert 调用频次（绝大多数题目仅出动 1 波）换取了最高级别的质量封口，使团队在代码实现与困难题上同样斩获 100.0 满分，总成本仅 $10.971，证明**固定拓扑的分工律动远胜盲目使用顶级模型**。

### 2. 团队角色的智力门槛与“降档失败”
- **为什么 Challenger 不能降档为 Junior**：
  TWR J+J+E（C4）试图通过将 Challenger 从 Senior（GLM-5.3）降为 Junior（Flash）以进一步降低成本。然而实测表明：
  - 在超难题 `uh2`（浮层穿透路由）中，降档审查员仅识别出 1/3 隐式契约，全组仅得 88 分（垫底）；
  - 在困难题 `nested_projection` 中，全组卡在 84 分，与 Single-GLM 相同；
  - 最终其 15 题总均分仅 97.2，落后于标准组（99.3），且由于前序漏洞漏检导致返工轮次拉长，总成本（$14.116）反而高于标准组（$10.971）。
  - **结论**：Challenger 承担主动寻找边界条件、对抗性验证的职责，必须维持在 Senior 及以上档位。

### 3. Expert 终裁在消除审查假阳性上的决定性价值
- **Clean PR 的“吹毛求疵”陷阱**：
  在 `astropy-3824` 这一无缺陷的真实代码合并审查中，Single-Flash、Single-Sol 与 TWR J+S（无裁决组）全军覆没，均仅得 40 分。它们将“上下文未展示完整导入语句”等非阻塞代码风格强行定性为严重缺陷打回；
- **终裁制度的纠偏机制**：
  TWR 标准组在 Challenger 阶段同样触发了假阳性误报（首交仅 70 分），但 Expert 终裁节点凭借深层逻辑辨识能力果断判定为 Clean 代码并予以放行，直接翻盘至 100 分。这证实了在代码审查和发布门禁中，**引入具备最高权威裁判权的 Expert 是防御假阳性、保障交付吞吐的必要设计**。

### 4. 无约束并发多 Agent 的物理覆写退化
- Free-Team 模式允许模型自由召集并行动，但在 `react_hook_form_task153` 中，两名子 Agent 在没有任务锁与文件修改权分离的保护下，几乎同时向同一源文件写入不同实现，造成物理内容相互撕裂与覆写，最终得分离奇跌至 60 分；
- TWR 的“单一可写 Owner”契约在物理层杜绝了并发改写的可能性，验证了多智能体软件研发工作流必须具备强互斥状态机。

## 七、工程落地选型与配置建议

综合全维度数据与成本效能比，针对不同软件研发场景给出以下工业级落地推荐：

1. **核心工程推荐：TWR J+S+E 标准组（默认主选）**
   - **适用场景**：复杂生产特性研发、跨模块重构、架构方案决策与核心组件发布门禁；
   - **推荐理由**：15 题全矩阵均分 99.3，代码与困难题双 100 满分，题均成本仅 $0.731，兼具最高级的工程安全性和极佳的算力经济性。
2. **极速预算推荐：TWR J+S（高吞吐开发档）**
   - **适用场景**：快速原型实现、单测编写、内部工具链维护等非生产门禁任务；
   - **推荐理由**：题均成本仅 $0.421，在代码实现类拿下 100 分；但因缺少 Expert 终裁，在代码审查和 Clean PR 放行时存在误报率，需配合人工把关。
3. **单模型慎用提醒：严防单模型盲目自审**
   - 单模型（如 Flash）无指导的自我反思常产生负向修改（ΔQ 倒扣分）；
   - 顶级单模型（如 Opus-5.5）虽然具备极强的逻辑上限，但单题成本动辄高达 $4~$8，在大规模 CI/CD 流水线中极易造成预算失控。
